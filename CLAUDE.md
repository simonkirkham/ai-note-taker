# AI Note Taker — Agent Instructions

This file is read by coding agents at the start of every session. Keep it lean.

## What this project is

A meeting-focused note taking app, now being **productionised** for long-term supportability — maintainable architecture, code-quality standards, performance, resilience, and operability. It began as a learning vehicle (event sourcing, .NET on AWS serverless, agentic dev workflows); that history explains existing choices but no longer drives new ones. Continued learning is now a secondary goal.

See [docs/goals.md](docs/goals.md) for the goals.

## Writing style

Applies to every generated doc **and** to conversational output.

- Facts over prose. Prefer tables and numbered lists to paragraphs.
- If a point fits a table row, it does not get a paragraph.
- One fact per point. No point spanning two sentences.
- Lead with the conclusion. Cut windup phrases ("In order to", "It's worth noting", "This document describes").
- No preamble, no restating the request, no summary of what you just did.

## Stack

- Backend: .NET 10 on AWS Lambda (ASP.NET minimal API behind a single Lambda)
- Event store: DynamoDB with a lightweight helper library
- Frontend: React + TypeScript (Vite)
- Infrastructure: AWS CDK in C#
- Tests: xUnit with plain C# Given/When/Then helpers; **BDD specs are mandatory**, never optional

## Layout

- `src/Api/` — ASP.NET minimal API hosted in Lambda
- `src/Domain/` — aggregates, commands, events
- `src/EventStore/` — DynamoDB event store and projection plumbing
- `src/Infrastructure/` — CDK app
- `tests/Domain.Specs/` — BDD-style Given/When/Then specs (one per slice); also event store unit specs
- `tests/EventStore.Integration/` — DynamoDB Local integration tests (Testcontainers)
- `tests/Api.Integration/` — in-process HTTP tests (WebApplicationFactory + in-memory stores)
- `tests/Api.Smoke/` — post-deploy smoke tests against real API; **fails the build** if `API_BASE_URL` is not set
- `tests/Infrastructure.Assertions/` — CDK template assertions (IAM, env vars, deletion policies)
- `tests/Browser.E2E/` — Playwright browser journey tests (BDD-style); **fails the build** if `FRONTEND_URL` is not set
- `web/` — React + TypeScript frontend
- `docs/` — architecture, roadmap (the index), ADRs, event model, learnings, and the standing planning docs (`future-features.md`, `technical-improvements.md`, `phases/phase-bugs.md`, `phases/phase-minor-changes.md`, `phases/phase-model-prompt-improvements.md`)

## How to run

```bash
# Activate pre-commit hook (once per clone)
git config core.hooksPath .githooks

# Build entire solution
dotnet build ai-note-taker.sln

# Run domain BDD specs
dotnet test tests/Domain.Specs/Domain.Specs.csproj

# Run in-process API tests (no AWS credentials needed)
dotnet test tests/Api.Integration/Api.Integration.csproj

# Run DynamoDB integration tests (requires Docker)
dotnet test tests/EventStore.Integration/EventStore.Integration.csproj

# Run CDK assertions
dotnet test tests/Infrastructure.Assertions/Infrastructure.Assertions.csproj

# Run post-deploy acceptance tests (requires deployed API)
API_BASE_URL=<api-gateway-url> dotnet test tests/Api.Smoke/Api.Smoke.csproj

# Run E2E browser journey tests (requires deployed frontend + Playwright browsers installed)
FRONTEND_URL=<cloudfront-url> dotnet test tests/Browser.E2E/Browser.E2E.csproj

# Run the API locally (Kestrel, not Lambda)
dotnet run --project src/Api/Api.csproj

# Validate infrastructure (requires dotnet publish first)
dotnet publish src/Api/Api.csproj -c Release -o src/Api/bin/Release/net10.0/publish
cdk synth

# Deploy to AWS
cdk deploy
```

## Helper scripts

Prefer these read-only wrappers over hand-rolling the underlying `gh`/`aws` commands — they bake in the CLAUDE.md logic, emit a one-line verdict, and cost fewer tokens.

| Script | Replaces | Output |
| --- | --- | --- |
| `scripts/deploy-status.sh` | the main-deploy merge-gate poll (`gh run list --branch main …` + quiescence reasoning) | `GREEN (#N) — safe to merge` / `IN PROGRESS` / `NOT SAFE`; exit 0 = safe |
| `scripts/merge-gate.sh <pr>` | the full Pip merge gate (mergeable + PR CI + main deploy) | one `MERGE GATE: GREEN/BLOCKED` verdict; exit 0 = safe to merge |
| `scripts/ci-logs.sh [pr\|run-id]` | finding the run id + `gh run view <id> --log-failed` (no arg = main's latest deploy) | failed-step logs |
| `scripts/eval-status.sh` | per-model progress of the latest eval run | progress table |
| `scripts/flake-watch.sh <since-deploy-#> [journey-regex]` | hand-counting clean deploy runs to prove a flake fix — scans **every attempt** of every deploy since the cutoff | per-deploy `clean`/`HIT` table + `clean=N` vs the 10-run target |

## Conventions

- **Specs first.** Every command requires a Given/When/Then spec before implementation. The spec is the source of truth for the slice.
- **A test failure not caused by the slice's change is a high-priority bug + immediate fast-follow — never shrug it off as "just flaky".** When a test fails during a slice and the failure is *not* attributable to the code change (a pre-existing flake, an unrelated env/timing race), file it in `docs/phases/phase-bugs.md` as a **high-priority** bug and flag it as **fast-follow work carried immediately after the slice merges** — do not let the slice absorb or silently mask it, and do not defer it indefinitely. Record it even if a re-run goes green; a flake that surfaced once will surface again in the deploy gate. (See the deploy-gate deflake guardrails — a "flaky" gate is often several stacked causes, sometimes hiding a real product bug.) **A flake fix is not `Done` on merge — it needs 10 clean deploy runs first.** The runs may come from *any* subsequent change's deploy, not just the fixing slice's own. Until the tenth, the row stays `In Progress` — "fixed <date>, awaiting 10 clean runs (N/10)". **Count with `scripts/flake-watch.sh`, never by reading run conclusions:** a deploy re-run into green still *contains* the failure, so only a run whose **every attempt** is free of the journey counts. Reading conclusions is exactly how BUG-38 was recorded as 6 recurrences when the real number was 26 — and 4 of the 12 deploys before the fix report `success` while hiding a `TagsJourney` failure on attempt 1.
- **A red shared build is a call to action — not a reason to wait or stop-and-ask.** When the deploy gate (or any build) goes red, default to **action**: diagnose the failure, and if it's your change fix it; if it's another slice's failure in the **shared** gate it is still yours to drive (a red gate blocks every slice + every parallel session). If you genuinely can't fix it, take a concrete unblock step anyway (re-run a *proven* flake, or quarantine-with-a-filed-bug as a last resort) **and** file the high-priority bug — don't park and "wait for the owner". Only stop-and-ask for genuinely destructive/ambiguous calls (reverting someone's slice, masking a real bug). Re-running is legitimate only for a *genuine* flake — a **deterministic** failure (same test every attempt) is a real bug; diagnose before you re-run. See [docs/learnings/act-on-red-builds-dont-wait.md](docs/learnings/act-on-red-builds-dont-wait.md).
- **Slice thin and vertical — ship value, prove fast.** Every slice is a *thin vertical* through all the layers it needs that delivers (or proves) **one** user-meaningful capability and is **independently shippable** — never a horizontal layer (all the backend, then all the frontend, then wire it up). When a capability is big or uncertain, find the **smallest slice that proves the whole flow end-to-end on one real call**, ship it, then scale the proven pattern outward. A slice that can't ship on its own, or that only makes sense once a sibling lands, is sliced wrong — re-cut it. (This is why Scout drafts slices by user value and Phase 15 was sliced by tab-of-value, not by layer.)
- **Event modelling drives design.** New commands and events are added to the event model first; see [docs/event-model.md](docs/event-model.md). Wire shapes for events live in [docs/event-schemas.md](docs/event-schemas.md); wire shapes for read projections live in [docs/view-schemas.md](docs/view-schemas.md).
- **Aggregates are pure.** No side effects, no DB calls, no clock — pass time and IDs in.
- **Events are immutable.** Once shipped, never edit shape; introduce a new event version instead.
- **Projections are rebuildable** from the full event stream. No state lives only in a projection.
- **Command handlers are append-only; the projector is the sole projection writer.** Each aggregate gets a `*CommandHandler` in `src/Api/CommandHandlers/`. The handler loads the stream, rebuilds the aggregate, executes the command, appends events with optimistic concurrency — and **stops there**, returning the new stream version as the read-your-writes token. It never writes a read model. Projections are built by `ProjectionUpdater` (the `SyncProjectingEventStore` decorator in tests/local, so `Api.Integration` reads are immediately consistent; the **Projector Lambda** off the DynamoDB Stream in prod). There is no `IDomainEventDispatcher`/`IDomainEventHandler` seam. A new projection is wired as fold logic in its `*Projection.Handle` (shared by the live projector and `ProjectionRebuildHandler`) plus an `EventDeserializer` arm — never inline in a command handler, never as a separate event-handler class. The projector is **at-least-once**, so gate projector DELETEs on current ownership, never delete by key alone. API endpoints do HTTP only — parse request, call handler, return result. Never write `store.ReadAsync` or `store.AppendAsync` inside an endpoint lambda. (This is the post-Phase-27-RYW shape; see [ADR 0009](docs/adr/0009-split-lambdas-cqrs-async-projectors.md).)
- **Optimistic UI updates.** The UI must reflect the user's action immediately — do not wait for the API response before updating local state. Apply the expected state optimistically; reconcile on error. Breaker must include this as an explicit acceptance criterion in the BDD spec for every slice with frontend changes. When adding a new async mutation handler, mirror the optimistic-first pattern of the nearest existing handler in the same component.
- **Learnings docs are named `phase-<phase><id>-<short-description>.md`** (e.g. `phase-4e-note-summary-cards.md`) and live in `docs/learnings/`. Never use `slice-` as a prefix. Not every slice earns a doc — the `process-improvements` skill tiers output: full doc only when there is a non-obvious *why* to preserve, else a one-line entry in `docs/learnings/_minor-log.md`, else nothing.
- **Work is tracked in one place per type, and `docs/roadmap.md` is the index that links to all of them.** Route each item by type: a **broken-down feature** → a numbered phase (`docs/phases/phase-N.md`); a **possible future feature** not yet scheduled → `docs/future-features.md`; a **bug** → `docs/phases/phase-bugs.md`; a **minor tweak** to existing behaviour → `docs/phases/phase-minor-changes.md`; a **model/prompt/analysis-quality improvement** (eval-driven) → `docs/phases/phase-model-prompt-improvements.md`; a **technical/infra/CI improvement** → `docs/technical-improvements.md`. The roadmap holds a one-paragraph summary of each phase and of each standing track, never the full content. When a future-features or technical-improvements item is picked up, it graduates to a numbered phase (features) or is actioned and removed (technical).
- **When the human raises a NEW feature, ask "file it or build it now?" in the SAME question batch as the scoping questions — never route it to `future-features.md` and then stop to offer Scout separately.** Routing (above) says where an unscheduled feature *lives*; it does not say the human wanted it parked. A feature request usually needs a shape decision anyway, so fold the schedule decision into that one `AskUserQuestion` — otherwise one request costs two interruptions (49-A: scoping questions → filed → "run it with scout" → phase doc → "run the pipeline"; the first two collapse into one). Same rule as the batching that already applies to any two decisions blocking the same next step.
- **Navigate docs via the index, not by reading the tree — links and summaries exist so you read one section, not ten files.** Every multi-doc area has a single index: `docs/roadmap.md` for phases and standing tracks, `MEMORY.md` for memory. Read the index first, then open only the specific doc/section it links to — never sweep a directory or read a whole phase doc to find one fact the `## Summary` table already answers. When writing: keep the index one line per entry and link to detail (`[phase-N.md](docs/phases/phase-N.md)`); put the fact in exactly one place and link to it from elsewhere — never inline the same content into two docs. A doc that must be read in full to be useful is mis-structured: add the index row or section anchor that lets a reader skip to the part they need.
- **A phase doc splits into a review surface and build notes, divided by a `---`. The human reads the review surface and stops; everything implementation lives below the divider.** This keeps the doc skimmable — the human reviews *how it works for the user and the value it brings*, never wades through event/projection/handler detail to find it. Structure, top to bottom:
  1. `**Goal:**` — **one** user-facing sentence: what the user can now do that they couldn't before. No history, no status narrative, no implementation. Status/history (deploy dates, PR numbers, what flaked) goes in a one-line `_(Done)_`-style title suffix or below the divider — never as prose above the table.
  2. `## Summary` table, immediately after `**Goal:**`, visible without scrolling. Numbered phases: `Slice | What the user gets | Status | Depends on`. Standing docs (`phase-bugs.md`, `phase-minor-changes.md`, `phase-model-prompt-improvements.md`): `Item | Summary | Status | Depends on`. One row per slice/item; the value column is **one line in user terms** — never names an aggregate, event, projection, or endpoint; `Status` is `Done` / `In Progress` / `Not Started` (numbered) or `Done` / `In Progress` / `Open` (standing); `Depends on` lists the required IDs or `—`. The table is the single at-a-glance source for status and dependency — no ASCII "slice order" diagram; ordering nuance goes in one line beneath the table.
  3. `## Slices` — the **review surface**. Per slice, only: `**User value:**` (one line) + `**How it works:**` (bullets — what the user *does* and *sees*, the interaction, key UX like optimistic/keyboard) + `**Scenarios (GWT):**`. Each scenario is a **named `Scenario:` block inside a fenced code box, with `Given` / `When` / `Then` on separate aligned lines** (the classic GWT layout — not one-line bullets); cover the happy path plus each meaningful edge, one scenario per behaviour, no scenario expanding into a paragraph. **Nothing in this section names an event, projection, handler, table, or endpoint** — if it does, it belongs below the divider.
  4. `---` then `## Build notes _(implementation — skip when reviewing)_` — **all** agent-facing detail, grouped per slice: acceptance criteria, commands/events, projections, API routes, tests, scoping decisions, plus the `Observability` and `Deploy-time` subsections. One bullet per fact; no narrative prose.
  - **Scout creates this; Scribe keeps `Status` in sync on every deploy** (see the scribe skill). The `## Writing style` rule governs the whole doc — facts over prose, one fact per bullet.

## Guardrails

- **Never big-bang a cross-cutting behavioural cutover — prove one vertical slice, then strangle the rest.** A change that flips behaviour across the whole app at once (a consistency model, a storage/transport swap, an auth or framework migration) exposes *every* dependent assumption simultaneously, so when one breaks the entire cutover reverts as a unit. Instead: prove the new path end-to-end on a **single real call** first, then migrate **flow-by-flow** with old and new coexisting until the last flow is moved — each step shippable and reversible. **Phase 27-C** flipped sync→async projections in one move; the frontend's read-after-write assumptions broke across every navigation at once and the whole cutover had to be reverted (see [`docs/learnings/phase-27c-async-cutover-reverted.md`](docs/learnings/phase-27c-async-cutover-reverted.md)). The vertical, incremental re-slice is [`docs/phases/phase-27-ryw.md`](docs/phases/phase-27-ryw.md) — RYW-1 proves one call (add a to-do), then scale. The lesson generalises: *the hard part is usually the cross-cutting contract (here, read-after-write), not the component you're adding — surface it on slice 1, don't discover it in production.* **Each strangle step that flips a read flow to async must also make every PRE-EXISTING E2E journey asserting that read reload-tolerant, in the same slice.** Journeys written for synchronous projection assert a freshly-written result immediately after a write+navigate with no reload; once the flow is async a cold/slow projector returns `stale` and the single read misses it. PR CI never catches this (E2E runs only in the deploy gate), so it costs a failed-deploy + roll-forward — RYW-2 (#255→#256) red-gated on `TagsJourney.AddTag_PillAppearsOnHomeCard` exactly this way. Grep the journeys for assertions on the now-async read and wrap them in a reload-to-re-gate helper (reload only while not-yet-visible → free when warm).
- **Deploy time is a first-class cost — flag it before merge; never silently slow deploys.** Deploys are a bottleneck, and a change that adds *per-deploy* time taxes every future change. Any change touching the deploy path (CI workflow, CDK that alters update behaviour, alias/traffic-shifting, bake windows, build steps) must state its deploy-time delta (faster / neutral / +N min, one-off vs recurring) in the PR and phase doc, and Hawk reviews it as a named check. A recurring per-deploy cost needs an explicit accept, not a silent introduction — and anything that holds the CloudFormation stack lock longer also serialises concurrent deploys into "another update in progress" failures. Match resilience cost to scale: traffic-shifting/canary bakes pay off only with real concurrent traffic (Phase 26-C's canary added ~5 min to every backend deploy for protection a single-user app rarely exercised — shipped then reverted same-day; see `docs/learnings/deploy-time-is-a-first-class-cost.md`).
- Never write directly to DynamoDB outside `src/EventStore/`.
- Never bypass the event store to mutate aggregate state.
- Never commit without all BDD specs green and `cdk synth` succeeding.
- Never edit a published event's shape — version it.
- **When versioning a previously-unversioned event, narrow its `EventDeserializer` arm and verify history.** Change the wildcard `(nameof(X), _)` arm to an explicit `(nameof(X), 1)` and add `(nameof(X), 2)`; confirm every historical write of that type used `InitialEventVersion` (= 1), or the narrowed v1 arm will throw on old events. Persist the new version under the **v1 logical `EventType` name** at the bumped `EventVersion` (see the `ContentEdited`→`ContentEditedV2` / `TagsSuggested`→v2 pattern in `NoteCommandHandler.ToEnvelopes`).
- **A new read projection ships empty — a deploy never populates it; trigger a backfill.** Deploying a slice that adds a projection creates the (empty) table but does **not** run the rebuild, so in prod the projection holds only entities written *after* the deploy. The feature then returns nothing in prod even though every test passes (Phase 22 search returned no results until the `NoteSearchView` backfill ran). After the deploy of any projection-adding slice, invoke `POST /admin/projections/rebuild` (authenticated) and verify the new table's item count matches the live count. This is a mandatory **Scribe** step for projection-adding slices.
- **A new field on an existing `*View` must be mapped in the DynamoDB store too — the in-memory test double hides the gap.** `InMemory*Store.UpsertAsync` keeps the whole view object by reference, so a new field round-trips for free and every `Api.Integration` test passes. But `DynamoDb*Store` maps **each attribute explicitly** (`UpsertAsync` writes named attributes; `MapItemTo*` reads them) — a field not added there **evaporates at the DynamoDB boundary** and is empty/default in prod while tests stay green (33-B2: `NoteDetail.OwnerName` folded + read in-memory but unmapped in `DynamoDbNoteDetailStore` → the headless re-analysis saw `""` in prod). When you add a field to a `*View`, update **both** stores **and** add a DynamoDB-Local (`EventStore.Integration`) round-trip test (set → `UpsertAsync` → `GetAsync` → assert it survived) in the same slice — the in-memory double structurally cannot catch it.
- **For an infra slice, "merged + a green deploy exists" ≠ live in prod — verify the resource.** The deploy gates the actual `cdk deploy` on `detect-changes backend=true`, and the production CDK deploy only runs after the E2E gate passes. So an infra slice whose own deploy **flakes at the E2E gate** reaches the *test* env but **skips `deploy-production`**, and a later *green* deploy triggered by a **test/web-only** commit has `backend=false` → `cdk deploy` is skipped → it is a **no-op for infra** and prod keeps the old stack. The change only ships when a later **backend** push triggers a full `cdk deploy --all`. The workflow is **push-only (no `workflow_dispatch`)**, and a re-run replays the run's *original* sha (stale once main moves). **Scribe must confirm an infra slice is actually live before marking it Done:** check the shipping deploy had `backend=true` *and* verify the resource in prod (`aws lambda list-functions --profile prod`, table/role present, etc.) — not just that "a green deploy exists." 27-D was merged + test-validated but not in prod until a later backend deploy (BUG-29) carried it — see [`docs/learnings/phase-27d-command-query-split.md`](docs/learnings/phase-27d-command-query-split.md). **Corollary — a route-contract slice is worse than a no-op when only the FRONTEND half ships:** if a slice changes both the web asset (new request path) and the backend (new API Gateway route / lambda mapping), and the backend is skipped (`backend=false`) while the frontend deploys, prod serves the *new frontend against the old backend* → the new path falls through to `/{proxy+}` → 404 (a live regression, not just "old behaviour"). 34-B's deploy flaked at `validate-frontend` (un-`scoped()` calendar msw handlers — relocating a route prefix means relocating its test doubles too), then a web-only flake-fix shipped the FE alone → prod calendar 404 until a backend push carried the routes. So for any slice that moves/renames an API route: confirm the **shipping** deploy had `backend=true` *and* probe the prod route (`aws apigatewayv2 get-routes`), and prefer fixing a pre-prod deploy failure with a change that re-triggers the **full backend deploy** — see [`docs/learnings/phase-34b-workspace-calendar.md`](docs/learnings/phase-34b-workspace-calendar.md).
- **Never begin a pipeline role's work without authorisation.** For roles triggered by a human brief (Scout, Breaker, Pip at slice start), wait for explicit human go-ahead. For roles triggered by an automated event defined in the workflow, proceed without asking — see the full automation chain below.
- **Never use the `Monitor` tool for CI/deploy waits — it prompts every launch.** `Monitor` is not in the permission allow-list, so using it to poll PR CI or the main deploy interrupts the human for approval on every routine wait (rejected in 43-A *and* 44-A). Instead poll with a single `Bash` helper-script call (`scripts/deploy-status.sh`, `scripts/merge-gate.sh <pr>`, `gh pr checks <n>`) or a `run_in_background` Bash `until`-loop that exits when the condition is met (one completion notification) — both are covered by `Bash(*)` + `autoAllowBashIfSandboxed` and never prompt. Same root cause as the sandbox escape-hatch: a prompt means the action isn't allow-listed — fix the mechanism, don't repeat the prompt.
- **Never prefix PowerShell commands with `cd`.** Use `npm --prefix <path> run build` (or equivalent flag) so the command starts with an already-allowed verb. `cd` is not in the allow-list.
- **Never use PowerShell compound statements starting with a variable assignment to pass multiline strings to CLI tools.** `$body = @"..."@; gh pr create --body $body` starts with `$body`, not `gh` — the permission checker won't match `PowerShell(gh *)` and will prompt for approval. Instead: use the Write tool to write the body to `.pr-body.md` (gitignored), then run `gh pr create --body-file .pr-body.md`. No variable assignment, no `Remove-Item`.
- **Doc edits to main are committed in the same turn they are made — never left dirty in the working tree.** A modified-but-uncommitted doc on main (roadmap, phase doc, learnings, README) is invisible to every parallel session, lost on the next worktree op, and silently masks the real status. When you edit a doc on main, commit it before ending the turn; if the tree is dirty for another reason (a human's WIP), stage only your own files by path and leave the rest. The one allowed exception is a human's in-flight WIP you did not create — never commit that for them. Scribe verifies a clean (or intentionally-staged-only) tree before handing off.
- **Never blind-`git add -A` / `git add .` into a `main` commit, and sanity-check the tree size before pushing to `main`.** A Scribe run once committed an unexpectedly near-empty working tree and **mass-deleted `main`** (−1056 files, the whole repo, leaving 2 docs) before pushing — caught only by a *parallel* slice's merge gate (`modify/delete` conflicts on core files; `git ls-tree -r origin/main | wc -l` = 2). Prod survived only because the bad commit never deployed (the last green deploy was on the good parent). **So:** stage Scribe's own files by explicit path (never `-A`/`.`), and before any push to `main` confirm `git diff --cached --stat` shows *only* the intended files and `git ls-tree -r HEAD | wc -l` is in the expected thousands, not a handful. **Recovery if it happens (non-destructive):** `git revert --no-edit <bad-sha>` to restore the tree, then `git checkout <bad-sha> -- <the few legitimately-changed files>` to preserve the real edits the bad commit also carried, then fast-forward push (no force).
- **Never commit slice work directly to main.** Breaker creates a branch **and a worktree** before the first test commit (see *Worktrees* below). All slice commits (Breaker, Pip, Refactor, Stylist, Hawk fixes) go to that branch. Pip opens a PR; Hawk reviews the PR; Pip squash-merges after approval.
- **Never merge into main unless main's deploy is green AND no deploy is in progress.** Before merging, Pip must inspect the *latest* deploy run on main — not just the latest *completed* one: `gh run list --branch main --workflow deploy.yml --limit 1 --json number,status,conclusion`. Merge **only** when `status` is `completed` **and** `conclusion` is `success`. If `status` is `in_progress` or `queued`, **wait for it to finish** — never merge while a deploy is running (its outcome is unknown, and merging stacks an unverified change on top and can disrupt the in-flight deploy). If `conclusion` is not `success`, stop and fix main first. Do **not** use `--status completed` for this check — that filter hides an in-progress run and will report a stale green. **A `--limit 1` snapshot is not enough on its own: a run that reached `completed success` can be *re-run* (by a parallel session or a retry), which flips the *same* run back to `in_progress`.** So a single poll can catch a transient green mid-re-run cycle — require **quiescence** (no `in_progress`/`queued` across the last few deploy runs, e.g. `--limit 5`), and if you have seen a run oscillate `completed → in_progress`, wait for it to settle definitively before merging. (27-D merged on a momentary green while #568 was re-running — see [`docs/learnings/phase-27d-command-query-split.md`](docs/learnings/phase-27d-command-query-split.md).) This is also enforced by the PR check workflow, which will block the merge automatically.
- **The PR's own CI checks must all be green before merge.** Confirm with `gh pr checks <n>` — every check must read `pass` (none `pending`, `fail`, or `cancelled`). PR CI is informational only for *when Hawk runs* (Hawk spawns the moment the PR opens, in parallel with CI — do not wait for CI to start the review), but it is a **hard gate for merging**: never merge a PR whose CI is still pending or failing. Note that `gh pr merge --auto` does **not** hold the merge for checks here (no required-status-check branch protection is configured), so it will merge immediately — do not rely on it; wait for `gh pr checks` to be all green yourself, then merge. **A `CONFLICTING` branch runs only head-only checks (e.g. CodeRabbit) — the merge-result checks (`backend`/`eventstore`/`frontend`) never start — so `gh pr checks --watch` can exit `0` falsely on a near-empty check list.** Before trusting green, confirm `gh pr view <n> --json mergeable,mergeStateStatus` is `MERGEABLE`/`CLEAN` **and** the expected backend+frontend checks are present and `pass`. If `CONFLICTING`, `git merge origin/main` in the worktree, resolve, re-run the gate, push — then re-check.
- **Never merge a `prototype/` branch into main or a `slice/` branch.** Prototype branches are reference material only. The one exception is cherry-picking the updated phase doc commit to main as part of the prototype exit procedure.
- **Before regenerating/committing `package-lock.json`, match CI's npm version exactly — not just the Node major.** CI is **Node 24** (per `.github/workflows/`); run `node --version` **and** `npm --version` and compare to the workflow. The skew is **bidirectional**: a lockfile cut on a *different* npm than CI's drops/adds optional native-binding entries (e.g. `@emnapi/core`, `@emnapi/runtime`) that the other npm expects, causing CI `npm ci` to fail with "Missing: X from lock file". This bit T1 in the *reverse* direction (local npm 11.6.2 < CI's 11.13.0 pruned entries CI wanted). If npm differs, `npm install -g npm@<CI-version>` then regenerate. **`npm ci` passing locally only proves the lockfile against *your* npm** — it is not evidence CI passes unless your npm == CI's. Regenerate **incrementally** from the committed lockfile (`npm install`), not from scratch (`rm package-lock.json`), or you may trip the pre-existing Tiptap exact-pin ERESOLVE (`@tiptap/extension-image` pinned vs floated `@tiptap/*` — dep-audit T6).
- **GitHub passes unset optional secrets as empty string `""`, not null.** When CDK props are populated from `${{ secrets.SOME_SECRET }}` and the secret is not configured in the environment, the value is `""`. Always guard optional config with `string.IsNullOrEmpty()`, never `!= null`.
- **Behind API Gateway HTTP API + Lambda, the trustworthy client IP is `HttpContext.Connection.RemoteIpAddress` — never raw `X-Forwarded-For`.** `Amazon.Lambda.AspNetCoreServer` populates `RemoteIpAddress` from `requestContext.http.sourceIp` (the AWS-computed TCP peer, non-spoofable for a regional `execute-api` endpoint). API Gateway **appends** the real peer to any client-supplied `X-Forwarded-For`, so the **left-most** XFF entry is attacker-controlled — reading it for an allowlist/rate-limit/ban makes it bypassable with one forged header. So allowlist on `RemoteIpAddress`. This bit 35-A: a review *mis*diagnosed `RemoteIpAddress` as "the proxy IP" and the resulting XFF "fix" was a spoofable security regression — caught only on adversarial re-review (validate a security fix against the **actual deployment topology**, not a generic "behind a proxy" assumption). Caveat: this holds because the route is on the **raw HTTP API**; if a path is fronted by CloudFront, `sourceIp` becomes a CloudFront edge IP and `RemoteIpAddress`-based allowlisting breaks. See [`docs/learnings/phase-35a-mcp-connect-list.md`](docs/learnings/phase-35a-mcp-connect-list.md).
- **Grant Lambda permissions via the resource (`resource.GrantX(apiFunction, …)`), never a bare `apiFunction.AddToRolePolicy(...)`.** Adding a fresh `Function.AddToRolePolicy` statement (especially a 4th one) interacts with the `CurrentVersion`/alias hashing and **silently drops** an existing *conditional* post-`CurrentVersion` grant — in Phase 25-A it deleted the `ssm:GetParameter` statement from the synthesised policy with no error. The resource-grant path (`table.GrantReadWriteData(fn)`, `bucket.GrantReadWrite(fn, "prefix/*")`) routes through `role.addToPrincipalPolicy` and does not. Likewise, a new bucket/table **env var** must ride the constructor `Environment` dict (create the resource *before* the Lambda) — `apiFunction.AddEnvironment(...)` after `CurrentVersion` is read is excluded from the function hash. **When a grant truly isn't resource-scopable (e.g. `transcribe:StartTranscriptionJob`), add it as a DEDICATED `new Policy(this, …, { Roles = [fn.Role!], Statements = […] })`, not `AddToRolePolicy`.** A role's auto-generated `DefaultPolicy` can be at the **6144-byte** managed-policy limit; growing it splits the overflow into a separate `AWS::IAM::ManagedPolicy` and *reshuffles which statements live where*, breaking unrelated grant assertions (33-B1: adding `StartTranscriptionJob` pushed `ssm:GetParameter` into the overflow → the SSM-grant + alarm-count tests failed). A standalone `Policy` keeps DefaultPolicy byte-identical, so every existing assertion stays green.
- **Google Calendar `Instances` endpoint: set `ShowDeleted = false` and `MaxResults ≥ 5`.** `MaxResults = 1` with a client-side cancelled filter silently returns null when the one fetched instance is cancelled, producing a spurious 404. `ShowDeleted = false` excludes cancelled instances server-side; a small lookahead buffer handles edge cases.
- **Never include request-contract fields that the handler does not use.** A field declared in a request record but never read by the handler is a contract lie — callers populate it, nothing consumes it, and the next developer will be misled. Delete unused fields before opening the PR.
- **When a response includes a boolean flag that enables navigation, include the required ID in the same response object.** A flag like `hasNextOccurrenceNote: true` is useless if the client must make a second call to discover the note ID. Return `nextOccurrenceNoteId` alongside `hasNextOccurrenceNote` so the flag is immediately actionable on page reload.
- **Use `Task.WhenAll` for independent async batches — never a sequential `foreach` over `Task`-returning calls.** If a set of store/API calls are independent (each takes different inputs, none depends on a prior result), start all tasks first and await together with `Task.WhenAll`. Sequential foreach adds latency proportional to N and is never correct for independent calls.
- **When changing a shared callback signature (e.g. `onOpenNote`), grep all call sites and wrapper components in the same PR.** Signature changes that widen or narrow parameters cascade through every component that wraps or re-exports the prop — a drift between wrapper type and caller type breaks the TypeScript build. Run `grep -r "onOpenNote\|propName"` before opening the PR and update every occurrence in one commit.
- **A test that mutates a process-wide environment variable must snapshot the original value and restore it in a `finally`, never force a literal (e.g. `null` or `"1"`).** The env var is shared across the whole test process and with CI. Forcing a literal leaks into other test classes (xUnit runs collections in parallel — disable parallelization for the assembly if a test must toggle a global) and, worse, can clobber a flag CI relies on: a test that forces `RUN_BEDROCK_EVAL=null` would silently turn the nightly eval into a no-op that still reports green. Capture with `var original = Environment.GetEnvironmentVariable(name);` and restore it regardless of outcome.
- **Never call `setState` synchronously inside a `useEffect` body — derive the transient state instead.** A reset/loading `setState` run directly in an effect (not in an async callback) trips `react-hooks/set-state-in-effect`, which `tsc` and `vitest` do **not** catch but `eslint` does — and lint is a hard CI gate. Instead of resetting a "browsed" slice to `null`/`loading` in the effect, key it by what it's for (`{ key, state }`) and **compute** the displayed value (`selected === key ? slice.state : loading`); the effect then only calls `setState` inside its `.then`. Run `npm run lint` on changed frontend files during Refactor, not just `tsc`/`vitest`.
- **When widening a shared TS type/interface (e.g. adding a field to `AuthState`), run `tsc -p tsconfig.test.json` locally and grep tests for object-literal constructions of that type.** CI typechecks the test sources with a **separate** `tsconfig.test.json`; a plain `tsc --noEmit` (app config) does not cover them, so a test that builds the type as a literal (missing the new field) passes locally and fails CI's "Typecheck (tests)" step. Caught BUG-15: `SignInPage.test.tsx` built an `AuthState` literal missing the new `authLoading` field. **Also run it after any `@types/*` major bump** — `@types/node@24` dropped a transitive `lib` reference that had been silently providing ES2022 `Array.at()` to the test typecheck, failing `tsc -p tsconfig.test.json` while `tsc -b` stayed green (dep-audit T1; fixed by making `tsconfig.test.json`'s `lib` explicit).
- **A session/state-recovery mechanism is only as good as the entry paths that call it — audit every consumer, especially cold start.** BUG-11 shipped a working refresh-token flow, but every caller (refresh timer, tab-visibility recheck, 401-retry) was guarded on an *already-present* token, so a cold load never used it and the session lasted ~1h not 30 days (BUG-15). When adding recovery logic, enumerate every entry path that should consume it and add a test that starts from the empty state, not a seeded one.
- **A retriable failure must never share a status code the client treats as success.** Since RYW, an exhausted append-retry contention threw `ConcurrencyException` → **409**, the same code a *genuine duplicate* returns and the client swallows as a no-op — so a lost write hid behind a phantom optimistic pill (BUG-27, real data loss). Map *retriable* contention to **503** (client retries until it lands) and reserve **409** for *terminal* conflicts. Generally: before reusing a status code, check what every client does with it — a code that means "give up, it's fine" must not also mean "try again."
- **E2E against the async projector must converge two ways — reload-tolerance AND a projector warm/drain — not either alone.** Since RYW, every projector-backed read is eventually consistent. (a) Route every post-write/post-navigation assertion **and action** (clicking a just-written element counts — `RemoveTagAsync`) through a reload-tolerant, token-re-gating wait; a bare `ToBeVisible`/`ClickAsync` races the lag. (b) The deploy gate must **warm and drain the projector to head** before the suite (write + poll `proj-position` until caught up) — reload-tolerance alone can't beat a cold projector seconds-to-minutes behind. When a deploy-gate flake won't die, get **per-attempt** failure data (`gh run view <id> --attempt <n> --log-failed` across *all* attempts, not just the latest) before inferring another fix — a flaky gate is often several stacked causes, and the per-test count is what separates them (and reveals the real product bug hiding among the flakes). See [docs/learnings/deploy-gate-deflake-stacked-causes.md](docs/learnings/deploy-gate-deflake-stacked-causes.md). **(c) Never make an *ungated* async read the incidental "click into the thing" step of a journey.** `/notes/search` is projector-built but has **no consistency token**, so a just-written note can lag the reload window with nothing to converge on — "wait longer" can't fix it. To E2E a navigation/URL behaviour, drive it through a **gated** read (`/notes/cards`) or pure client-side state, not search: CHANGE-23 opened the note from search results and flaked deploy #633; re-cut to drive the gated home-card list via the show-older filter (#634 green). See [docs/learnings/phase-23-url-filters-back-navigation.md](docs/learnings/phase-23-url-filters-back-navigation.md).
- **An E2E diagnostic must never read a response/request BODY, and must surface evidence through the THROWN message — plus every E2E test gets a hard per-test timeout.** A `page.Response` listener that read each body via `response.TextAsync()` in a fire-and-forget task hung the whole E2E suite for **44 min** (deploy #592): on a reload loop `ReloadAsync()` aborts in-flight requests, and `TextAsync()` on an aborted response never resolves, blocking teardown. Record **only synchronous properties** — `response.Url`/`.Status`, `request.Method`/`.PostData` — never the body. And xUnit **swallows `Console.WriteLine` on passing tests and never flushes a hung one**, so route diagnostics through the **thrown exception message** (visible in `--log-failed`): on a reload-loop deadline `catch (PlaywrightException)` and `throw new Exception($"…page.Url + rendered state + recorded sync request URLs…")`. (A 30 000 ms `System.TimeoutException` in a stack is a `WaitForResponse`/`ClickAsync` action timeout, *not* an assertion timeout — `PlaywrightException` — which localises *which* call failed.) Every journey uses `[E2EFact]` (`FactAttribute` with `Timeout=120_000`) so one stuck call can't hang the gate; **verify the timeout fires** (xUnit's `Timeout` is silently ignored when parallelization is disabled — confirm with a throwaway probe). See [docs/learnings/e2e-gate-hang-and-the-diagnostic-that-caused-it.md](docs/learnings/e2e-gate-hang-and-the-diagnostic-that-caused-it.md).
- **Never authorize (existence/ownership) against an async projection — read a strongly-consistent source.** Every note-scoped handler checked ownership via `noteDetailStore.GetAsync` then 404'd on null; since RYW that projection is built async, so any op right after `POST /notes` 404'd "not found" while the projector lagged (BUG-30, the biggest residual flake). When you migrate a read model inline→async, audit every handler that *reads it to make a decision* (auth, existence, conflict), not just ones that return it — they silently become racy. Authorize from the event stream (Command Lambda) or a same-stream-gated check. **Corollary — the Query Lambda (27-D) has no event-store access**, so an event-stream auth fix that works for writes **500s** for reads; in-process `Api.Integration` runs a single host without the split and won't catch it. And **DynamoDB Streams don't guarantee cross-key order** — gating a read on stream A's position while reading a projection built from stream B is a race (the B fold can lag). See [docs/learnings/authz-on-async-projection-and-the-observability-blindspot.md](docs/learnings/authz-on-async-projection-and-the-observability-blindspot.md).
- **Before trusting any AWS log/metric, confirm the resource belongs to the environment under test.** A full night went into querying CloudWatch that all looked healthy — because the deployed **E2E env is a different AWS account** than `--profile prod`. Resolve the stack's `WebUrl`/distribution and check the account first. When you can't reach an env's server logs, route the evidence through a channel you *can* read (e.g. a Playwright `Response` listener printing failing `/api` responses into the gh run log). And drive autonomous rerun loops **strictly sequentially** (one deploy in flight at a time) — parallel fire-and-forget reruns jam the CloudFormation stack-lock and look like a hang.

## Worktrees

Each slice runs in its own git worktree so multiple slices can run in parallel without interfering with each other.

**Breaker sets up the worktree** at the start of every slice:

```bash
# From the main checkout
git worktree add ../ai-note-taker-slices/slice-5e-my-feature -b slice/5-e-my-feature
```

The worktree lands at `../ai-note-taker-slices/<slice-name>/` (a sibling of the main checkout, outside this repo). All slice work — tests, builds, `npm install` — runs from inside that directory. The main checkout stays on `main` and is never touched during a slice.

> **Use an absolute path for `git worktree add`.** The shell cwd may be a subdirectory (e.g. `web/`), in which case `../ai-note-taker-slices/...` resolves to `ai-note-taker/ai-note-taker-slices/...` — nesting the worktree *inside* the repo. Pass the full absolute sibling path (and `git -C <repo-root>` if unsure of cwd).

**After the slice branch is merged and deleted**, remove the worktree:

```bash
git worktree remove ../ai-note-taker-slices/slice-5e-my-feature
```

**First-time setup in a fresh worktree** (Breaker does this immediately after `git worktree add`):

```bash
dotnet restore ai-note-taker.sln
npm --prefix web install
```

Prototype branches follow the same pattern: `git worktree add ../ai-note-taker-slices/prototype-<name> -b prototype/<name>`.

## Workflow

1. Plan mode for any non-trivial slice.
2. **Breaker creates the worktree** — `git worktree add ../ai-note-taker-slices/<slice-name> -b slice/<phase>-<id>-<short-description>`, then `dotnet restore` + `npm --prefix web install` inside it. All subsequent work happens from that directory. Set the session name to the slice name using `/rename <slice-name>`.
3. **Prototype** *(UI-heavy or UX-uncertain slices only)* — run the `prototype` skill before touching the event model. Skip if the interaction is obvious CRUD. Prototype code is quick-and-dirty scaffolding on a `prototype/<slice-name>` branch/worktree pushed to remote — never merged. On approval, the exit procedure rewrites `docs/phases/phase-X.md` on main with confirmed GWT scenarios and UX patterns. Real implementation starts fresh from the updated phase doc, not from prototype code.
4. Update event model.
5. Write BDD spec.
6. Implement until spec passes green.
7. **Refactor** — run the `refactor` skill against all changed files; re-run specs after each fix.
8. **Stylist** (user-facing slices only) — run the `ui-ux-pro-max` skill to apply visual polish; re-run tests after.
9. Open PR. After every `git push` to a PR branch, immediately schedule a CI monitor (`gh pr checks <n>` every 60s) — do not wait to be asked. CI results are informational; they do not block Hawk.
10. **Open PR → Hawk** — spawn `agent-skills:code-reviewer` subagent to review the PR immediately; do not wait for CI results.
11. **Hawk approves → Pip checks gates, then merges** — before running `gh pr merge --squash --delete-branch`, confirm **both**: (a) the PR's own CI is all green (`gh pr checks <n>` — every check `pass`, none pending/failing), and (b) main's *latest* deploy run is `completed`+`success` with no deploy in progress (`gh run list --branch main --workflow deploy.yml --limit 1 --json number,status,conclusion` — wait out any `in_progress`/`queued` run; do not use `--status completed`). **`scripts/merge-gate.sh <n>` checks both gates in one call** (exit 0 = both green). If either gate is not met, stop and wait/investigate. No user confirmation needed once both gates are green. Note: `--delete-branch` deletes the *remote* branch server-side but its *local* cleanup fails with `'main' is already used by worktree` (main is checked out in the primary worktree) — this is harmless; the squash merge still succeeds. Do local cleanup separately in step 13 (`git worktree remove` + `git branch -D <slice-branch>`).
12. **Hawk requests changes → Pip fixes** — fix every finding, push, re-run Hawk.
13. **Merge to main → remove worktree + delete local branch + monitor deploy** — run `git worktree remove ../ai-note-taker-slices/<slice-name>`, then `git branch -D slice/<phase>-<id>-<short-description>` to delete the now-merged local branch (the `--delete-branch` at merge only removed the *remote* branch; the local one lingers). Then immediately schedule a monitor on `gh run list --branch main --limit 1` (or poll `scripts/deploy-status.sh`). Poll every 90s until the deploy run completes. Stale merged branches accumulate fast — never skip the local delete.
14. **Deploy succeeds → Scribe** — run all Scribe steps without being asked:
    - Create `docs/learnings/phase-<n><id>-<short-description>.md`; carry out all Done actions immediately
    - Mark slice/phase status as Done in `docs/phases/phase-N.md`
    - Update `docs/roadmap.md` if the phase is now complete
15. **Deploy fails → investigate and fix** — read `gh run view <id> --log-failed` (or `scripts/ci-logs.sh`), diagnose, fix, push. Do not stop to report unless genuinely blocked.

### Human gates (the only steps that require explicit user confirmation)
- Slice start: Scout brief, Breaker spec writing, Pip implementation start
- `cdk deploy` when run manually (not when triggered automatically by a merge to main)

If you find yourself asking the user to approve any other step, check this list. If it is not a defined human gate, proceed autonomously.
