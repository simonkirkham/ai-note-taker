# Phase Bugs — Defect backlog

**Goal:** A standing, unnumbered phase that captures bugs found in the deployed app and tracks them to a fix. Unlike numbered phases, this has no learning theme and no fixed slice sequence — items are added as defects surface and removed (marked Done) as they are fixed. Each bug is still fixed the normal way: a failing spec/test that reproduces it first, then the fix.

**What belongs here:** defects — behaviour that is wrong, broken, or crashes. If it's a small adjustment to working behaviour it's a **minor change** ([docs/phases/phase-minor-changes.md](phase-minor-changes.md)); a new capability is a **feature** ([docs/future-features.md](../future-features.md) → a numbered phase); a refactor/upgrade/CI item is a **technical improvement** ([docs/technical-improvements.md](../technical-improvements.md)).

**Learning surface:** none specific — this is maintenance work. The discipline is reproduce-before-fix (the Prove-It pattern) and guarding against regression.

## BUG-38 — `TagsJourney` deploy-gate flake — a network-timed autofocus steals focus and unmounts the tag input

**Status:** In Progress — root-caused 2026-08-06 after ~4 months of wrong theories; fix in PR #418, awaiting the clean-run bar. **Severity:** High — the worst single deploy-gate flake by a wide margin, **and a real user bug**, not a test artefact.

**Measured scale (per-attempt scan of deploys #627–#719, 93 deploys):** 58 failing-test occurrences, of which **26 (45%) are `TagsJourney`** — nearly 4× the next worst journey — across 15 deploys and hitting **all six** of its tests (`AddTag_PillAppearsOnNoteScreen` 8, `AddTag_PersistsAfterNavigation` 7, `AddMultipleTags_SpaceSeparated` 4, `AddTag_PillAppearsOnHomeCard` 3, `RemoveTag_PillDisappears` 2, `RemoveTag_GoneAfterNavigation` 2). This doc previously recorded **6** recurrences — the 4× undercount is failures that were re-run into green and never written down, which is why the standing rule is to count per-attempt with `scripts/flake-watch.sh`, never by reading run conclusions.

**Symptom:** a `TagsJourney` test times out at 30 s waiting for `GetByTestId("tag-input")` in `AppPage.AddTagAsync`.

**Root cause (`web/src/components/NoteView.tsx:267-269`):**
```
useEffect(() => { if (!loadingDetail && !notFound) inputRef.current?.focus(); }, [loadingDetail, notFound])
```
This focuses the **title** input. It does **not** fire on mount — it fires when the RYW-gated `GET /notes/{id}` resolves, i.e. at an arbitrary wall-clock moment (~150 ms to the 8 s gate cap) while the whole screen, `CommandBar` included, has been interactive the entire time. The tag combobox dismisses itself on blur (`TagCombobox.tsx:107` → `CommandBar.tsx:81` `setAddingTag(false)`), which **unmounts** the input — so the focus grab destroys it mid-interaction. `AddTagAsync` fills then presses Enter as two Playwright round trips; a steal landing between them detaches the element Playwright already resolved, and because `addingTag` is now false, `tag-input` never returns.

**Enter is not the trigger** — Playwright's `press` checks connectedness *before* dispatching the key, so the detach necessarily preceded the keystroke.

**Real user impact:** start typing a tag on a freshly-opened note and the box can be ripped away, with your half-typed text silently submitted.

**Every previous theory is retired:**
| Retired theory | Disproved by |
|---|---|
| Cold start / idle gap | #649/#652/#654/#656 are same-or-next-day; #719 failed 43 s in, after 27 tests had already passed (warm) |
| Projector lag / stale gated read | Lag cannot detach a DOM node; the failing call is an **action**, and the assertions were already reload-tolerant |
| The app never loaded | The #719 log shows the input **resolved**, with `value="1:1s"` |
| A `notFound` bounce | Not reachable on a note that had already rendered |

Lag is the trigger's **timing source**, never the fault — which is why every consistency-token and reload-tolerance fix looked relevant and none worked.

**Method note worth keeping:** the breakthrough came from the deploy #719 call log, the first to carry a `locator resolved to …` line. ## BUG-56 — On-device transcription: nothing live while recording, very slow after stop

**Status:** **Done** — #426, deploy #729. Verified headlessly; the Windows checklist (MANUAL-VERIFICATION §BUG-56) is the remaining real-world proof. **Severity:** High — the headline benefit of 48-A / [BUG-52] / [BUG-53] is absent in the shipped installer, and it fails **silently** (no banner, no log the user can see).

**Reported:** 2026-08-06, real Windows testing. This is the [BUG-53] Windows validation coming back negative — BUG-53 shipped (#413, deploy #715) marked Done *pending* that validation.

**Symptom:**
- Nothing appears in the transcript for the whole recording.
- After Stop, text eventually appears — after a long wait.
- No on-device-failed banner at any point.

**Root cause — THREE stacked faults, root-caused from the code (2026-08-07), not from the installer.** The originally-filed "prime hypothesis" (the never-ready silent stall) is real but is the *third* layer, not the cause.

1. **The resident server has never once started — the wrong binary is spawned.** `WhisperServer` is constructed with `whisperBinPath()`, which returns **`whisper-cli.exe`** (`desktop/src/modelStore.ts:142`); no server-binary resolver existed. `whisper-server` and `whisper-cli` are **different binaries** in the same whisper.cpp bundle: only the server accepts `--host`/`--port` and serves `/inference`. The CLI exits immediately on the unknown argument, so `start()` never reaches ready and the live path produced nothing from the moment [BUG-53] shipped. `whisper-server.exe` **is** in the pinned v1.9.1 release zip and **is** staged by `fetch-whisper-bin.mjs` (it copies every `.exe`) — nothing ever pointed at it. **Confirmed on Windows 2026-08-07:** no `whisper-server.exe` in Task Manager during a recording; `resources/whisper/` present.
2. **The failure was invisible because the banner is unreachable during a recording.** `local:error` *does* fire and `useTranscription` *does* `setError(...)` — but `RecordControl.tsx:120` rendered the banner only when `status === "error"`, and the local-error handler deliberately leaves `status === "recording"` (audio is still captured for the stop-time pass). So the message was stored in React state and never rendered. This is why the user saw silence rather than the start-failure banner that was, in fact, being sent.
3. **The silent-stall hole** as originally filed: `StreamingSession.step()` returns quietly while `!server.ready`, before the `FAIL_THRESHOLD` accounting, so *process alive, never ready* is silent forever. Not the cause here, but it is the reason fault 1 could hide at all.

The post-stop delay is the unchanged [BUG-52] final pass: `small.en` over the **entire** recording via the CLI at ~2.3× realtime — ~13 min for a 30 min meeting. Nothing is wrong with it; it was just the only path still producing output. **Expected cost, not a defect.**

**Why every test was green:** `whisperServer.integration.spec.ts` takes its binary from **`WHISPER_SERVER_BIN`** — an env var supplied by hand — while production resolved `whisperBinPath`. The spec proved `WhisperServer` works against the *server* binary; nothing asserted that production wires that same binary. Same class as the [BUG-53] learning "a replaced component's half-wired contract is a lie until you re-check every consumer" — here the unchecked consumer was the *binary path*, not the error channel.

**Reproduce-before-fix:** not E2E-provable (needs real capture on Windows — MANUAL-VERIFICATION §BUG-53). Headless coverage added, red before the fix:
- `desktop/tests/whisperPaths.spec.ts` — the server path resolves to `whisper-server`, is a sibling of the CLI, and `WHISPER_BIN` must not redirect it.
- `desktop/tests/streamingSession.spec.ts` — a stub server stuck `running && !ready` past the deadline calls `onError` exactly once; one that becomes ready in time reports nothing.
- `web/src/__tests__/RecordControlLocalError.test.tsx` — the banner renders while `status === "recording"`/`"finalising"` when `error` is set.
- `desktop/tests/packaging.spec.ts` — packaging verifies **both** binaries were staged.

**Fix (this PR):**
1. `whisperServerBinPath()` in `modelStore.ts` resolves `whisper-server(.exe)`, overridden by `WHISPER_SERVER_BIN` (deliberately *not* `WHISPER_BIN`); `local:start` passes it to `ensureServer`, keeping `whisperBinPath` for the batch passes.
2. `RecordControl` renders the banner whenever `error` is set, not only on `status === "error"`.
3. A ready deadline armed in `StreamingSession.start()` (45 s, one-shot, independent of the step cadence) fires `onError` if the server never reaches ready. It must sit **below** `WhisperServer`'s 60 s start timeout: `start()` kills the child and nulls `proc` when it gives up, so a deadline at or above that can only ever observe a dead process. The first draft was 75 s and was therefore unreachable dead code — a mechanism that read as a live safety net and was not, which is the very shape of this bug. `streamingSession.spec.ts` now asserts the ordering so it cannot silently invert again.
4. The same check runs on `stop()`, so a recording that ends before the deadline does not finish silently — with a 20 s grace period, since the first recording after launch legitimately spends seconds loading `base.en` and a banner there would sit beside a perfectly good transcript. A start failure that lands *after* the renderer stops listening is held and replayed on the next recording, so a permanently-stalled engine cannot stay silent for someone who only records briefly.
5. `WhisperServer.start()` handles the `ChildProcess` `'error'` event — an ENOENT on a missing binary previously had **no listener**, so it would have thrown inside the Electron main process instead of rejecting `start()`.
6. `fetch-whisper-bin.mjs` fails packaging unless **both** `whisper-cli.exe` and `whisper-server.exe` staged, and stages only the two binaries actually invoked rather than all 23 `.exe` files in the release zip.

**Deploy-time:** desktop-shell only — no backend, no CDK, no web deploy path touched → neutral.

## BUG-65 — on-device live transcription runs, but far slower than the ~3-4 s target

**Status:** In Progress — PR #435. **Severity:** Medium-High — [BUG-56] made the live path *exist*; this is what stands between it and being usable. No data loss (the stop-time transcript is unaffected).

**Reported:** 2026-08-07, Windows, on the installer carrying the BUG-56 fix. `whisper-server.exe` visible in Task Manager, live text appearing — "very slow".

**Diagnosis (from code + the pinned whisper.cpp v1.9.1 server source). Not yet measured on the machine.**

| # | Cause | Where | Why it costs |
|---|---|---|---|
| 1 | `--audio-ctx` never passed | `whisperServer.ts` `start()` args | whisper encodes a **padded 30 s mel every time**, so a 3 s window costs nearly what 30 s does. Likely the dominant cost. **Correction:** an earlier version of this row claimed whisper.cpp's `stream` example lowers this for streaming — it does **not** (`stream.cpp` defaults `audio_ctx` to 0, the full context). The 768 figure comes from the `command` example, a short-utterance workload, and `whisper.h` labels the option EXPERIMENTAL and quality-reducing. |
| 2 | temperature fallback | `server.cpp` | `temperature_inc = 0.20f` default → a segment failing the logprob/compression heuristics retries at 0.2, 0.4 … 1.0, up to ~6 decodes, and a sliding window's clipped boundary words are what trip those heuristics. **NOT FIXED, deliberately.** `--no-fallback` is parsed by the server and never read (`cli.cpp`/`stream.cpp` do `no_fallback ? 0.0f : …`; the server assigns unconditionally) — dead in every release through v1.9.1. The only working lever is a per-request `temperature_inc`, which also disables whisper's repetition guard — and a reduced `audio_ctx` is documented to *induce* repetition loops, so it would trade latency for a hallucination risk this change itself creates. Left in place; measure first. |
| 3 | `maxWindowMs = 8000` | `streamingTranscript.ts` `DEFAULT_STREAM_CONFIG` | the reducer commits nothing until the window exceeds 8 s, so steady state re-transcribes **8-16 s** every 1.5 s tick — 3-5× the ~3 s window `whisperServer.ts`'s header comment claims. |
| 4 | `floor(cores/2)`, cap 8 | `localEngine.ts` `pickThreads` | correct for [BUG-52]'s CPU-peg complaint, but it halves the latency-critical path too. whisper-server's own default is `min(4, hw)`. |

**Ruled out:** beam search. The pinned `server.cpp` has `beam_size = -1`, and `strategy = beam_size > 1 ? BEAM_SEARCH : GREEDY`, so it is already greedy. (Checked rather than assumed — this was the first hypothesis and it was wrong.)

**Why (1) and (2) hit the live path specifically:** both defaults are tuned for *batch* transcription of complete audio. The live path re-transcribes a short, boundary-clipped, overlapping window many times per minute — the workload whisper.cpp ships a separate `stream` example for.

**The asymmetry that makes this cheap:** the live transcript is **disposable**. 48-B re-transcribes the entire recording with `small.en` on stop and replaces it. Live accuracy can therefore be traded aggressively for latency with **zero effect on the saved note** — the opposite of the trade-off that governs the final pass.

**Instrument before tuning.** Right now `whisper-server`'s stdout is not captured and `StreamingSession` logs no per-step timing, so there is no way to tell which cause dominates or to prove an improvement. This is the [BUG-56] lesson applied: do not ship a mechanism whose effect cannot be observed. Log per step: window ms, inference ms, and whether the step was dropped by the busy-guard.

**Fix (PR #435) — instrument and tune together, so one installer round-trip both improves it and reveals what is left:**
1. Pass `--audio-ctx 768` to the live server only (`--no-fallback` is dead in the server and `--flash-attn` already defaults true — neither is passed). Verified from the pinned `server.cpp` parser, not from the binary's symbol table — a symbol table shows a flag is *present*, never that it is *read*, which is exactly how the dead `--no-fallback` nearly shipped as a fix. The batch/diarize CLI path stays untouched.
2. Lower `maxWindowMs` so the steady-state window is a few seconds.
3. Reconsider the thread split: the live server is latency-critical and short-lived per step; the batch pass is the one that must not peg the machine.

**Verified about the shipped binary before changing any flag** (an unknown argument makes whisper-server print usage and `exit(0)` — the exact mechanism that killed the live path in BUG-56):
- `--audio-ctx` consumes a value and is read. `--no-fallback` parses but is **never read** by the server — parsing is not the same as taking effect, and checking only the former is what nearly shipped a no-op as a fix.
- `--flash-attn` is **already `true` by default** — passing it would be a no-op, so it is not passed.
- `beam_size = -1` already selects greedy, so beam search was never the problem (the first hypothesis, checked and discarded).

**Not done, deliberately:** raising the thread count. It would re-open [BUG-52]'s CPU-peg complaint, and every change here reduces *work* rather than spending more CPU. If the log shows it is still short, threads are the next lever with data behind them.

**Deploy-time:** none — desktop-shell only.

**Deploy-time:** neutral — a cancellation deadline plus one metric filter/alarm; no traffic-shifting, no IAM change. Note the guardrail on alarms: adding one changes the alarm-count infra assertion, so update `InfraAssertionsTests` in the same slice.

## BUG-59 — A save into a deleted note says "try again" forever

**Status:** Open. **Severity:** Medium — no server-side data loss, but the user's typed text is held only in the tab and is lost when it closes, with the UI insisting a retry will work.

**Found:** observability-review 2026-08-06. Explicitly deferred as secondary by [BUG-44] ("save-against-deleted shows a *retriable* 'try again': out of scope, not carried") — this row carries it with prod evidence.

**Symptom:** the note editor stays open on a note that no longer exists. Every save toasts "Couldn't save your note. We kept your text — try again." The retry can never succeed.

**Prod evidence** — note `b721c995-f1de-442a-8fb9-2d4e6bde176a`, 2026-07-24, one real browser session (`Mozilla/5.0 (Windows NT 10.0)`, not the smoke suite):

| Time (UTC) | What happened |
|------------|---------------|
| 14:34:09 | `CreateNote` → v2, then `RenameNote`/`SetNoteDate`/`LinkNoteToCalendarEvent`/`SetNoteDate` → v6 (create-from-meeting flow) |
| 14:34:21 | `DeleteNote` → **`NoteDeleted` v7** (confirmed as the last event on the stream in `notetaker-events`) |
| 14:34:33 | `RenameNote` → 404 `NoteNotFoundException` |
| 14:37:06 / 14:41:34 / 14:53:28 / 14:54:27 / 15:05:51 | `EditContent` → 404 ×5 |

31 minutes of editing, six rejected writes.

**Root cause:** `NoteView.handleSaveContent` (`web/src/components/NoteView.tsx`) has exactly two failure branches — `StaleContentError` → the conflict banner, everything else → the generic retriable toast. A 404 (note deleted) lands in "everything else", which is wrong: it is terminal, not transient. Nothing invalidates the note query on that 404 either, so the cached detail keeps the editor alive and the existing `is404 && onNotFound` bounce (`NoteView.tsx:250`) never fires.

**Observable?** Yes — `Command failed EditContent Note NoteNotFoundException` at Warning. But it is **indistinguishable in the error view from the deliberate 404 probes in `tests/Api.Smoke/ErrorResponsesSpec.cs`**, which fire a `RenameNote`/`EditContent`/`SetNoteDate` triplet against random GUIDs on every deploy (45 of the window's 51 `NoteNotFoundException` warnings). Separate them on `user_agent`: the smoke probes carry `Amazon CloudFront`, a real user carries a browser UA.

**Reproduce-before-fix:** delete a note in one tab while its editor is open in another, then type and save in the second tab — expect the deleted-note state, not the retry toast.

**Fix direction:** treat a 404 from a note write as terminal. Invalidate `keys.note(noteId)` so the existing not-found path takes over, and replace the toast with a "this note was deleted" state that surfaces the kept text for recovery (copy out / recreate) rather than inviting a retry that cannot succeed.

**Deploy-time:** frontend-only → neutral.
