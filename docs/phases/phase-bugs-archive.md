## BUG-1 — Blank screen presented when 401 returned from API

✅ PR #99, 2026-06-02. Cold-load fetches went out before `AuthProvider`'s effect seeded the in-memory token → 401, which `apiFetch`'s `&& token` guard swallowed → blank screen. Fix: seed the token synchronously in the `useState` initialiser; on any 401, `apiFetch` does one deduped silent refresh-and-retry, else routes to sign-in.

## BUG-2 — favicon.ico request 404s / errors on every page load

✅ PR #103, 2026-06-02. No `<link rel="icon">` and no `favicon.ico` → the browser fell back to a 404'd `/favicon.ico`. Fix: added `web/public/favicon.svg` + an explicit icon link; an asset-assertion test guards it. _(The recurring `TopK`/`webgl` console warning is an injected browser extension, not this app.)_

## BUG-3 — ASP.NET Data Protection warnings on every Lambda cold start

✅ PR #108, 2026-06-02. Three Data Protection fallback warnings per cold start dominated the "All errors" widget. The API uses bearer tokens only (no cookie auth / antiforgery / `IDataProtector`), so Data Protection is genuinely unused → `Builder.cs` filters the category below Error (suppress-at-source).

## BUG-4 — `ConcurrencyException` surfaces as an unhandled 500 on note writes

✅ PR #107 (with BUG-5), 2026-06-02. Optimistic-concurrency conflicts on note writes had no handler/global mapping → 500. Fix: the global handler in `LoggingConfig` maps `ConcurrencyException` → 409 at one cross-cutting point. (Benign races were later also retried — BUG-17.)

## BUG-5 — Renaming a deleted/non-rebuildable note throws an unhandled 500

✅ PR #107 (with BUG-4), 2026-06-02. A pre-check read the eventually-consistent projection, then the domain guard threw a raw `InvalidOperationException` (uncaught) → 500. Fix: `NoteCommandHandler` rebuilds from the stream and throws typed `NoteNotFoundException` via a new `Note.Exists` predicate; the global handler maps that → 404, uniform across all note writes.

## BUG-6 — CloudWatch RUM receives no data (loader CDN host is regional)

✅ `hotfix/12-f-rum-cdn-host`. The RUM loader URL used `client.rum.eu-west-2.amazonaws.com` (NXDOMAIN) — the aws-rum-web loader CDN is global, served only from `us-east-1`; only the data-plane `endpoint` is regional. Fix: hard-code `us-east-1` for the loader host in both deploy jobs; keep `endpoint` regional. Not caught by any gate — a literal string that only fails at runtime DNS in a real browser.

## BUG-8 — `x-correlation-id` returned to clients is never emitted as a log field

✅ PR #125, 2026-06-02. The `x-correlation-id` header/body was set from `TraceIdentifier` but never appended to the Powertools logger → a user-quoted ID returned 0 results in logs. Fix: append it as the queryable `correlation_id` field on every log line. (The bearer token is still never logged.)

## BUG-9 — Note tab panels stack below Quick notes instead of replacing it

✅ PR #156, 2026-06-03. `.panel { display:flex }` beat the `hidden` attribute's UA default → inactive tab panels stayed laid out. Fix: `.panel[hidden] { display:none }`. jsdom doesn't apply CSS Modules so component tests passed blind → guarded by a real-browser `NoteTabsJourney` E2E. Lesson: CSS-driven visibility must be guarded at the browser layer.

## BUG-10 — Live transcription falls progressively behind realtime

✅ PR #158, deploy #445, 2026-06-03. The AudioWorklet posted ~8 ms (128-sample) chunks → ~125 SigV4-signed event-stream events/sec, more main-thread overhead than sustainable → an audio backlog that never drained. Fix: coalesce to ~100 ms PCM chunks (`PcmChunker`, ~10/sec) + throttle partial-result re-renders to ≤1/200 ms.

## BUG-11 — User is signed out too frequently

✅ PR #175, deploy #469, 2026-06-05. Sessions lasted ~1 h because the only refresh was a hidden-iframe `prompt=none` flow modern browsers block (third-party cookies); no refresh token was ever requested. Fix: a backend refresh-token flow — `access_type=offline`, refresh token in an `HttpOnly; SameSite=Strict; Path=/api/auth` `rt` cookie, `POST /auth/refresh` exchanges it; iframe deleted. The 30-day window slides on each refresh.

## BUG-14 — Pasting space-separated tags intermittently drops a pill

✅ PR #205, deploy #495, 2026-06-09. On a freshly-created note `patchTags` no-ops when the note isn't cached, the in-flight GET resolves tagless, and `onSettled` invalidated only `keys.tags` → the first of two concurrent tag adds was lost. Fix: invalidate `keys.note` only when the optimistic patch couldn't apply (`ctx.previous === undefined`). Misdiagnosed first as latency (a 15→45 s timeout bump disproved it — a pill that never renders in 45 s is missing, not slow).

## BUG-15 — Forced through full Google sign-in on cold load (refresh cookie unused at bootstrap)

✅ PR #209, deploy #500, 2026-06-10. Every refresh trigger was guarded on an already-present token, so a cold load (expired token discarded) never tried the `rt` cookie → session effectively ~1 h not 30 days. Fix: a one-shot cold-start `attemptSilentRefresh()` in `AuthProvider` (when no token + no OAuth `code`), behind an `authLoading` spinner so sign-in never flashes; preserves the BUG-1 token-before-first-fetch invariant. Lesson: audit every entry path that should consume a recovery mechanism, especially cold start.

## BUG-16 — Google emails the user on every login (`prompt=consent` forces a consent grant)

✅ PR #215, deploy #504, 2026-06-10. `prompt=consent` was hard-coded on every auth URL (added in BUG-11 to guarantee a refresh token) → a fresh consent grant + security email each sign-in. Fix: send `prompt=consent` only when a `google_refresh_established` localStorage flag is absent; set on any token acquisition, cleared on every refresh-failure path (incl. the 401 branch). The backend already never clobbers an on-file token with an empty one.

## BUG-17 — Concurrent multi-word tag add silently drops a tag (no handler retry on conflict)

✅ PR #217, deploy #506, 2026-06-10. BUG-4 mapped a conflict to 409 but never retried, so a benign same-stream race still lost the second tag (its phantom pill then 404'd on removal). Fix: a bounded retry (read→rebuild→handle→append, 4 attempts) on `ConcurrencyException` in `NoteCommandHandler`; `untagNote()` treats 404/409 as OK. Aggregate stays pure.

## BUG-18 — Removing an inline image (or any content edit) is silently not persisted

✅ PR #232, deploy #520, 2026-06-11. Content saved only on editor `onBlur`; the Save button navigated without flushing, and removing an image kept focus off the body → no blur → the draft was discarded (silent data loss). Fix: a ref-guarded `handleSaveContent` flushes on leave (Save/back) and unmount, restores on error; `deletingRef` skips the flush on delete. The 25-D E2E removed a never-persisted image (no-op PUT) so it shipped blind.

## BUG-19 — Inline image flashes a 403 on every open (raw key rendered before resolve)

✅ PR #232, deploy #520, 2026-06-11. `ImageNodeView` first painted the bare S3 key as `<img src>`, which the browser resolved relative to the SPA route (`/notes/notes/…` → 403) before `resolveImages` swapped in the presigned URL. Fix: render a placeholder span while `isImageKey(src)`. (This only suppressed the rendered node, not the parse-time fetch — see BUG-24.)

## BUG-21 — Note title silently lost when navigating in and out of a note

✅ PR #258, deploy #547, 2026-06-13. Title was seeded once from a prop (never reconciled with `detail.title`) so it could show empty; the auto-focused input's blur then persisted that empty value (`HandleRename` had no guard) → permanent loss in the stream. Fix: migrate title to the draft pattern (`titleDraft ?? detail?.title`); `handleSaveTitle` no-ops empty/whitespace/unchanged; domain `HandleRename` guards `IsNullOrWhiteSpace`. Write-up: [phase-bug21-note-title-draft-reconcile](../learnings/phase-bug21-note-title-draft-reconcile.md).

## BUG-22 — Multi-tag add drops a pill under RYW-2 async reads — consistency-token slot overwritten by an older version

✅ PR #262, deploy #551, 2026-06-13. Under RYW-2 async reads, two concurrent same-stream tag POSTs returned `@N`/`@N+1`; the per-stream token slot was last-writer-wins, so the older `@N` could win and the next gated read released before the second tag folded (the server never flags `stale`, so the retry loop couldn't rescue it). Fix: keep the **highest** version in the slot (`setStreamToken`/`setLatestToken` max-version, per-stream). Resolved the reopened [TI-19](../technical-improvements-archive.md#ti-19) `TagsJourney` flake (20/20 first try). Follow-up: tag-pill asserts made reload-tolerant.

## BUG-23 — Projection rebuild returns an unhandled 500 on a transient DynamoDB timeout

✅ PR #269, deploy #558, 2026-06-13. The rebuild's *writes* retried but the heavy *reads* (`ReadAllStreamsAsync`, reconcile scans) were unwrapped, so a transient `TimeoutException` aborted the whole rebuild → 500. Fix: a generic `BoundedWrites.WithRetryAsync<T>` wraps every rebuild read; a surviving timeout / non-client cancel maps to a retriable **503** at Warning (a genuine client abort still → 500).

## BUG-27 — Concurrent multi-tag add silently drops a tag (exhausted-retry 409 treated as a duplicate no-op)

✅ Done (under TI-39). On retry exhaustion `NoteCommandHandler` rethrew `ConcurrencyException` → 409, which the client treats as a duplicate-tag no-op → the loser's write was silently dropped under a phantom optimistic pill. Aggravated by 27-D (separate Command-Lambda invocations). Fix: throw `WriteContentionException` on exhaustion → a retriable **503** (distinct from the duplicate 409); `MaxAppendAttempts` 4→6; client retries 503, throwing on the final attempt so a never-landing write rolls back. Lesson: a retriable failure must never share a status code the client treats as success.

## BUG-28 — Concurrent multi-tag add-then-remove drops a write (DynamoDB `TransactionConflict` escaped as an unhandled 500)

✅ Done. The loser of two concurrent `TransactWriteItems` on one stream's META row is cancelled with reason `TransactionConflict`, but `DynamoDbEventStore.AppendAsync` only translated `ConditionalCheckFailed` → `ConcurrencyException`, so the conflict escaped as an unhandled 500 and (not being `ConcurrencyException`) was never retried → silent drop. Not reproducible in-process (the in-memory store has no transaction-conflict semantics). Fix: classify `TransactionConflict` as a retriable `ConcurrencyException` too (extracted + unit-tested); protects every aggregate's concurrent writes.

## BUG-29 — Projector can't purge note images on delete (role missing `s3:ListBucket`)

✅ Done, 2026-06-13. The Projector role had `GrantDelete` (DeleteObject only) but `PurgeNoteAsync` **lists** objects first → every `NoteDeleted` purge threw `AccessDenied (s3:ListBucket)` (caught at Warning), orphaning images in S3 indefinitely. A 27-RYW/27-D IAM gap. Fix: add `imagesBucket.GrantRead(projectorFunction, "notes/*")` (ListBucket+GetObject) alongside GrantDelete; CDK assertion requires a List action (still no PutObject).

## BUG-30 — Note-scoped handlers authorized against the async NoteDetail projection → 404 after create under load

✅ Done. Every note-scoped handler checked ownership via the async `NoteDetail` projection then 404'd on null, so an op right after `POST /notes` hit a not-yet-built projection → a 404 storm under the E2E write burst (invisible in single-user prod; invisible to investigation because the E2E env is a separate AWS account). Fix: (a) writes authorize from the strongly-consistent **event stream** via a shared `INoteAuthorizer` in the Command Lambda; (b) the `GetActions` read (Query Lambda, no event-store access) keeps the projection but adds a bounded re-poll for the cross-stream fold race. Lesson: never authorize against an async projection.

## BUG-31 — A browser test ("remove an image, reopen the note") randomly fails during deploys

✅ PR #397, deploy #701, 2026-07-23. `NoteImageJourney.Remove_an_image` randomly red-gated deploys, blocking unrelated releases. **Three stacked causes:** (1) the removed image genuinely reappeared after reopening — fixed by the wider read-after-write work (TI-39 projector warm-up + [BUG-30] event-stream ownership); (2) `SaveAndReturnAsync` waited for a `GET /notes/cards` request the page can serve from its in-memory cache, so the wait timed out at 30 s — fixed (PR #297) by waiting for the home screen instead, which de-flaked the whole suite, not just this test; (3) the #697 failure was **not** a slow reopen — a stale gated refetch transiently **blanked** the note ([BUG-48]), which flips the header Save→Cancel by design (`hasContent` false), so `save-button` was genuinely absent. Fix: the test keeps durable local draft body text so `contentDraft` is non-null and `hasContent` stays true through removal+save — **deterministic**, so the stale-refetch race can no longer change the outcome. Also raised the `ConsistencyGate` cap **2 s → 8 s** (PR #377, deploy #681) after prod showed 11 gate timeouts in 14 days, the worst shape a cold overnight projector (`lastSeq=-1`, no recorded position within budget). The first re-enable attempt (PR #393, reload-tolerance on the *reopen*) addressed the wrong cause and was reverted (PR #395). Confirmed **6/6 clean** gate passes (#701–#706). Keeping the projector warm so cold reads are *fast* is deferred as TI-52.

## BUG-33 — Forced through full Google consent after inactivity (warm-tab refresh skips the `rt` cookie)

✅ Done 2026-06-22, slices **30-C** + **30-B**. Returning to a backgrounded tab showed the full Google sign-in **and scope-approval screen** (~twice a day) despite a valid 30-day `rt` cookie — same user-facing symptom as the supposedly-fixed [BUG-15]/[BUG-16]. Two warm-tab paths treated an expired in-memory token as a dead session **without first attempting a silent refresh**, and both cleared `google_refresh_established` (which forces `prompt=consent` on the next sign-in): `AuthContext.onVisibilityChange`'s `if (remaining <= 0) handleRefreshFailure()` branch (only `remaining < REFRESH_LEAD_MS && > 0` tried the cookie), and `useGoogleAuth.scheduleRefresh`'s `if (delay <= 0) { onRefreshFailure() }`. Chrome freezes background-tab timers, so the proactive 5-min-lead refresh never fired while hidden and `remaining <= 0` was the common case on refocus. Prod confirmed the diagnosis: every Google `/token` call returned **200** on a clean ~55-min cadence and the sign-outs produced **no** failed Google call — the failure short-circuited client-side and never reached `/auth/refresh`. Fix: 30-C collapses both paths into an `attemptSilentRefresh()` first, failing (and clearing the flag) only on a null result; 30-B removed the flag-driven `prompt=consent` forcing entirely, so even a genuine sign-out no longer re-triggers consent. The warm-tab sibling [BUG-15] missed — that fix added only the **cold-load** bootstrap refresh. (Confirmed during diagnosis: the OAuth app is **Published**, so token expiry was never a factor.)

## BUG-34 — In-progress transcript lost on browser-back; re-record couldn't recover it

✅ Done, 2026-06-22 (PR #306, deploy #606). Alt+← (popstate) while recording silently unmounted the note: `beforeunload` doesn't fire on SPA nav and the leave-confirm was wired only to the in-app Save button, so the fire-and-forget unmount commit was aborted on a true page exit → first recording never committed. Re-record couldn't recover it: "Continue" keyed only off the *committed* transcript (`hasInitialTranscript = transcriptText !== null`), so a fresh recording started empty and its commit deleted the note-keyed draft. Confirmed in prod (note `0a449915…`): only the *second* recording's `TranscriptionCompleted` (v41) existed; draft table empty. Fix: (a) popstate guard in `NoteView` (trap history entry → leave-confirm; "Leave & save" exits via `onExit` to a fresh route, not `navigate(-1)` which the trap absorbs) + a `pagehide` keepalive flush in `useTranscription` writing the finalised tail to the loss-tolerant **draft** (never a premature commit); (b) draft-aware Continue — `NoteView` feeds an interrupted draft into `RecordControl` so Record offers Continue seeded from it. Frontend-only; the popstate guard's full browser-history nav is unprovable in jsdom (`BrowserRouter`, no `useBlocker`), so data-safety rests on the unit-tested pagehide flush + unmount commit. See [learning](../learnings/phase-bug34-transcript-leave-guard.md).

## BUG-35 — Fuzzy search over-matches ("Andrew" returns notes containing "and")

✅ Done, 2026-06-22 (PR #312, deploy #612). `NoteSearchRanker.Score` ranked a query against each **whole field** with `Math.Max(Fuzz.PartialRatio, Fuzz.TokenSetRatio)`. `PartialRatio` slides a query-length window across the entire body and keeps the best substring match — over a long note there are hundreds of windows, so a 6-char query almost always found an "and…" window scoring ≥ the 60 threshold. Matching was substring-based, not word-based. Fix: word-level matching — a query term matches a document **token** only by (1) exact equality, (2) prefix (term ≥ 3 chars; `Andrew`→`Andrews`), or (3) tight whole-token `Fuzz.Ratio ≥ 85` (term ≥ 4 chars; `planing`→`planning` ≈ 93, `and`→`andrew` ≈ 67 rejected). Inclusion gates on the strongest single-term hit (OR semantics across a multi-word query); ranking uses the mean per-term score (rewards full coverage) with the existing 1.5 title weight. 4 regression tests (name-vs-"and", prefix, infix, multi-word OR) + preserved typo test; query-time change in the ranker so no projection backfill needed. See [minor-log](../learnings/_minor-log.md) 2026-06-22 BUG-35.

## BUG-37 — The ✓ "Mark as discussed" tick on a note heading no longer works

✅ Done, 2026-06-25 (PR #344, deploy #645). The floating ✓ tick fires `editor.commands.toggleStrike()` while the selection is only a **collapsed caret** inside the heading (the button renders on `isActive('heading')`, no text selected). ProseMirror `toggleMark`/`toggleStrike` on an empty selection only sets a **stored mark** (it would strike the *next typed* char) — it never strikes the existing heading text, so nothing visibly happened. The click handler was unchanged since 7-B; 7-B's "renders with strikethrough" acceptance was hand-checked, never covered by an automated test, so the regression (surfacing across the TipTap v2→v3 line) went unnoticed. Reproduced empirically first: caret-only `toggleStrike` yields no `~~` in the serialized markdown; range-selecting the heading text first does. Fix: extracted `web/src/lib/headingDiscussed.ts` — `markHeadingDiscussed(editor)` range-selects the heading (`$from.start()`→`$from.end()`) then `toggleStrike`, guarded on `isActive('heading')`; the ✓ button calls it. New unit spec `headingDiscussed.test.ts` drives a real headless `Editor` with the same collapsed caret the button produces (strike-on, toggle-off, heading-only, empty-heading no-op), RED-first then GREEN. Frontend-only, no event/projection change. See [minor-log](../learnings/_minor-log.md) 2026-06-25 BUG-37.

**Follow-up (PR #347, deploy #648) — the actual primary cause.** #344's fix was real but *secondary*: the tick still did nothing in the real browser. Root cause: the ✓ button is `position:absolute` with **no z-index**, and the editor content `.contentInput` is `position:relative` (added in Phase 25 for inline-image positioning) — so the content is a positioned sibling in the *same* stacking layer and, coming later in the DOM, paints **over** the button, swallowing every click (the click landed on the heading, not the button). Invisible to jsdom (no layout/hit-testing), which is why #344's unit tests were green while the feature stayed dead. Proven in a real browser (Playwright): `elementFromPoint` at the tick centre returned `<h2>` before the fix and the `BUTTON` after; a normal click then strikes the topic. Fix: `z-index:1` on `.discussedButton`. Added `DiscussedTickJourney` (Browser.E2E) — a normal `ClickAsync` on the old code times out with "`<h2>` … intercepts pointer events"; passes on the fix. Both fixes are needed: #347 makes the click land, #344 makes a caret-click strike the whole heading. See [minor-log](../learnings/_minor-log.md) 2026-06-25 BUG-37b.

## BUG-39 — Todo reorder reverts after reload (deployed only)

✅ Done 2026-06-26. Dragging BBB above AAA then reloading reverted the order — deployed-only and deterministic (5/5 across deploy #656 and its reruns). **Root cause, from the test-env Projector Lambda log (`Projector skip todo-order#__default__ at 1: position_guard`): `clear-test-data` wiped `notetaker-events` and the projection tables but **not** `notetaker-proj-position`**, the projector's per-stream processed-sequence store. The default workspace's order stream `todo-order#__default__` has a **stable id reused every run**, so once any run set its position to seq 1 that mark survived the clear; every later run re-appends its reorder as seq 1 (events re-numbered from 0), which is `≤` the stale mark → the position guard skips it as an already-seen duplicate → positions are never applied → `GET /todos` falls back to `AddedAt` order. Entity streams (`note#`, `todo#<guid>`) dodge it because each run uses fresh guids; only **stable-id** streams collide. Not a product bug and **not 36-B** — that correlation was coincidental (#655 was the run that first set the mark, and it passed). Fix: `clear-test-data` also clears `notetaker-proj-position` plus the previously-omitted projection tables (`notesearchview`, `workspacelist`, `actionfeedback`, `tagfeedback`, `calendarlinkindex`); `TodoReorderJourney` un-quarantined. No test below the deploy-gate E2E can catch it — `Api.Integration.TodoReorderTests` covers the exact scenario and passes, because `SyncProjectingEventStore` applies events synchronously in append order and `InMemoryTodoListStore` has no `attribute_exists`/PutItem semantics (the documented in-memory-double blindspot). **Latent, not the trigger:** the per-item `Position` design is independently fragile — `DynamoDbTodoListStore.SetPositionAsync` silently swallows `ConditionalCheckFailedException` (an unprojected row permanently loses its position), `PutAsync` is a full `PutItem` that clobbers `Position` back to null on re-projection, and the `todo-order#` and `todo#` streams have no cross-key order. An order-snapshot redesign (the full ordered id list on one per-workspace row, items ordered by index) would immunise all three; file to `technical-improvements.md` if pursued.

## BUG-40 — Blank lines a user adds for structure are stripped on save

✅ PR #363, deploy #666 (`70c87c4`), 2026-06-26. Frontend-only. A note typed with blank lines between sections was condensed into a single tight block on save. Note content persists as **markdown**, serialized from the Tiptap doc by `ed.storage.markdown.getMarkdown()`; markdown represents a paragraph break as exactly one blank line and has **no representation for an empty paragraph or consecutive blank lines**, so `tiptap-markdown`'s default serializer collapsed every run to one. The collapse was client-side at serialize time — nothing downstream (handler, `ContentEdited`, projection, DynamoDB) trims. Fix: `web/src/lib/blankLineParagraph.ts` — `BlankLineParagraph` replaces StarterKit's bundled Paragraph (`StarterKit.configure({ paragraph: false })`) and serializes an empty paragraph **that is not the last child of its parent** as a single U+00A0 line, which survives the round-trip and reloads as a genuinely empty paragraph; re-saving is idempotent and non-empty content is untouched. The last-child guard keeps the editor's auto-trailing caret paragraph and a fully-cleared note from persisting a stray U+00A0. Added `@tiptap/extension-paragraph@3.23.4`, exact-pinned to the StarterKit-transitive version (matching the `@tiptap/extension-image` pin) to dodge the tiptap ERESOLVE peer conflict. 11 cases in `blankLinePreservation.test.ts`. Deferred cosmetic: a blank-line note's card preview can carry a literal U+00A0 (`MarkdownStripper` doesn't strip it) — harmless, since downstream `IsNullOrWhiteSpace` treats U+00A0 as whitespace.

## BUG-41 — HTTP action-item endpoints: object-level auth gap (IDOR)

✅ PR #370, deploy #674. Broken object-level authorization on the HTTP action-item surface: `ActionItemHandlers.{Complete,Reopen,Edit,Delete}ActionItem` authorized the **route `noteId`** via `OwnsNoteAsync`, then called the command handler with **only** the `actionId` — and `ActionItemCommandHandler.ExecuteAppendAsync` read only the action stream, never checking the action's recorded owning note (`ActionItemAdded.NoteId`) or stamped owner. So the route `noteId` was validated but unbound: owning *any* note plus knowing a foreign `actionId` let you mutate that action, stamped with your `sub`. Practically gated (the `actionId` is an unguessable random GUID and every listing endpoint filters to the caller's own items, so foreign ids are not enumerable) and not a regression — the gap always existed. Found by Hawk during the 41-B review, which fixed the MCP equivalent and deliberately left the HTTP surface to keep the slice tight. Fix: the four mutation handlers authorize the action's own owner via `IActionItemAuthorizer.OwnsActionAsync(actionId, sub)` (Command Lambda, event-stream read) instead of the route note; a foreign **or deleted** action now returns 404 (deleted previously returned 409).

## BUG-42 — `CreateAndListNoteJourney` E2E flake — post-create list assert races the projector

✅ PR #371, deploy #673. `CreateAndListNoteJourney.Create_a_note_name_it_and_see_it_in_the_list` red-gated deploy #667 attempt 1 (passed on rerun), unrelated to the 41-B change that triggered it. Since RYW the home card list (`GET /notes/cards`) is projector-built and eventually consistent, but the journey asserted the new card with a bare 15 s `ToBeVisibleAsync` and **no reload in the wait** — a cold or lagging projector simply misses the window. Same class as [BUG-25]/[BUG-26] (post-write visibility vs projector lag), **not** the [BUG-38] cold-start `tag-input` app-load stall. Fix: both create→list asserts — `CreateAndListNoteJourney` and `NoteDeleteJourney`, which had red-gated #672 the same way — use the reload-tolerant, re-gating `AssertNoteVisibleInListAfterReloadAsync`; the bare racy helper was removed so it can't be reintroduced. Reproduce-before-fix was impractical (pure timing); the reload-tolerant assert is the guard. Its residual limit surfaced later as [BUG-49] — reload-tolerance re-gates a read that will converge, but cannot beat a projector that hasn't started.

## BUG-43 — Query Lambda 500 on the first request after a SnapStart restore

✅ PR #379, deploy #682. A user-facing read returned **500** on a cold start (`GET /w/__default__/todos`): `AmazonDynamoDBException: "The security token included in the request is invalid."`, `cold_start: true`, logged seconds after a `RESTORE_START`. 1 occurrence in 30 days across all five log groups; transient (the next request succeeds), so too rare to trip `notetaker-error-rate` but visible in logs. Root cause: SnapStart captures the snapshot at end-of-init, and the `RegisterBeforeSnapshot` priming hook (`Builder.cs`, calling `IDynamoHealthCheck.CheckAsync`) exercises the SDK credential chain — so a security token is cached **in the snapshot** — while no `RegisterAfterRestore` hook existed to reset it. Query-only because only that function sets `SnapStartConf.ON_PUBLISHED_VERSIONS`. **The obvious fix was wrong** (verified 2026-06-30, AWSSDK v4): `FallbackCredentialsFactory.Reset()` is `[Obsolete]` — clients resolve via `DefaultAWSCredentialsIdentityResolver`, so it clears a cache the live clients no longer use — and it doesn't address the documented root, which is that under SnapStart the runtime serves **container** creds (`AWS_CONTAINER_CREDENTIALS_FULL_URI`) while the SDK cached the access-key **env-var** creds frozen in the snapshot. Fix: the Query Lambda's DynamoDB client binds a swappable credentials holder that a `RegisterAfterRestore` hook flips to fresh `GenericContainerCredentials`, gated Query-only via `SNAPSTART_CONTAINER_CREDS` (Command untouched). Prod-verified — flag live on the Query function, no `security token` errors post-deploy. Suspected at the time to be the common root of the cold-start E2E gate flakes ([BUG-38]); those recurred afterwards, so it was real but not the whole story.

## BUG-44 — Deleted note reappears in the list (delete not consistency-gated) → reopen+save 404s

✅ PR #382, deploy #685, 2026-07-01. **High — silent loss of the user's typed content.** Deleting a note left it in the list and openable; reopening and saving it 404'd ("couldn't be saved"), the text was lost, and the note then vanished. Delete was the one note write that never surfaced or threaded a read-your-writes token — `DeleteNote` emitted no `X-Consistency-Token` and `deleteNote` used plain `requestVoid` — so `useDeleteNote`'s `onSettled` `/notes/cards` refetch ran **ungated** against the async projector, returned the still-present (not-yet-`NoteDeleted`) card, and undid the optimistic removal. Confirmed in prod (note `996cf435`, 2026-07-01 07:30 UTC): RUM showed `DELETE 204` → repeated `GET /notes/cards 200` → `PUT …/content 404`. Same class as [BUG-30]/[BUG-22]/[BUG-27]. Fix: `DeleteNote` captures the append `version` and calls `SetConsistencyToken` (mirroring `DeleteTag`); `deleteNote` uses `requestVoidWithResponse` + `captureNoteToken` so the cards refetch gates on the projector dropping the note. Tests: `NoteReadYourWritesTests.DeleteNote_ReturnsConsistencyTokenHeader_AtNextVersion` + `GetNoteCards_WithDeleteToken_ExcludesTheDeletedNote`, and `noteConsistency.test.tsx` "carries the delete write token". The secondary symptom — a save into a deleted note surfaces the *retriable* "try again" rather than a terminal message — was deliberately not carried (the gate stops users reaching it via the list) and was later filed on its own as [BUG-59].

## BUG-45 — Move-to-workspace / folder moves not consistency-gated

✅ PR #384, deploy #689, 2026-07-01. Found by Hawk reviewing #382 — the same ungated-cards-refetch defect [BUG-44] had just fixed, on the three note-move paths. `moveNoteToWorkspace`/`moveNoteToFolder`/`unfileNote` used plain `requestVoid` (no token capture) and the matching handlers never called `SetConsistencyToken`, so `useMoveNote*`'s `onSettled → invalidate → getNoteCards` ran ungated against the async projector: a note moved to another workspace reappeared in the source workspace's list, and folder moves flickered placement. No data loss. Fix: all three handlers capture the append `version` and call `SetConsistencyToken` (`HttpResponse` auto-injected); the api fns use `requestVoidWithResponse` + `captureNoteToken` — the **note-cards** scope `getNoteCards` gates on, not `captureFolderToken`. Tests: `NoteMoveReadYourWritesTests` (token at v+1 per path; a token-gated source-workspace cards read excludes the moved note) + `noteConsistency.test.tsx` parametrised over all three fns. The folder-delete cascade of the same class was left open as [BUG-46], because it produces *N* note-stream writes against a list gate that holds only a single stream token.

## BUG-47 — Stale-read note edit silently overwrites real content (no version guard) → data loss

✅ PR #392, deploy #696. **High — real data loss:** a full note was wiped in prod (recovered from the event stream and restored). A user edited a note, navigated away and returned; the note showed **empty**; they retyped what they remembered, and the save replaced the original with the fragment — no warning, no conflict. Prod evidence (stream `note#c7b3b612…`): `v5 ContentEdited` 2134 chars @09:04:06, `v6` 30 chars @09:04:14, the fragment verbatim the last bullet of v5. v5 was durably stored the whole time; only the read model reflected v6. **Three combining gaps:** (1) the note-detail read is served by the async projection behind a best-effort gate that caps at 8 s and then returns the current projection with a `stale` header, while the client `gatedRead` retries only 2×/300 ms and **returns the stale body anyway** (a missing token reads ungated); (2) the Tiptap editor is **uncontrolled** — content is taken once at `useEditor` construction with no later value-sync, and `LazyNoteEditor` is keyed by `noteId`, so navigate-back **remounts** and reseeds from `contentDraft ?? detail?.content ?? ""`, making a stale-empty read the editable baseline; (3) `EditContentCmd` had no check that the client had seen the latest content — the event store's append-level optimistic concurrency guards the *store* version, not the version the *client* was looking at, so the overwrite appended cleanly. Fix: **hash-based optimistic concurrency on content edits** — the client sends the SHA-256 of the content it loaded, the aggregate compares it to a hash of its current `_content`, and a mismatch returns a **terminal 409** (not 503 — a retry can't help, per [BUG-27]), surfaced as a non-destructive conflict banner that keeps the typed text and offers "Load latest content". Hash chosen over a content-version field (which would need a `NoteDetail` field mapped in **both** stores plus a round-trip test and a projector change) and over the whole-stream token (which false-conflicts on an interleaved tag/date write); `ContentEdited`'s shape is unchanged, so no event versioning and no prod backfill. Explicitly rejected: a size/shrink heuristic (can't distinguish a deliberate select-all-delete from a stale wipe) and server autosave (would persist stale-empty state *faster*). The read-side analogue — a stale refetch regressing the cached detail — remained open as [BUG-48]. See [learning](../learnings/phase-bug47-stale-read-content-overwrite.md).
