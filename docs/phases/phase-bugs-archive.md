## BUG-1 — Blank screen presented when 401 returned from API

✅ PR #99, 2026-06-02. Cold-load fetches went out before `AuthProvider`'s effect seeded the in-memory token → 401, which `apiFetch`'s `&& token` guard swallowed → blank screen. Fix: seed the token synchronously in the `useState` initialiser; on any 401, `apiFetch` does one deduped silent refresh-and-retry, else routes to sign-in.

## BUG-2 — favicon.ico request 404s / errors on every page load

✅ PR #103, 2026-06-02. No `<link rel="icon">` and no `favicon.ico` → the browser fell back to a 404'd `/favicon.ico`. Fix: added `web/public/favicon.svg` + an explicit icon link; an asset-assertion test guards it. _(The recurring `TopK`/`webgl` console warning is an injected browser extension, not this app.)_

## BUG-3 — ASP.NET Data Protection warnings on every Lambda cold start

✅ PR #108, 2026-06-02. Three Data Protection fallback warnings per cold start dominated the "All errors" widget. The API uses bearer tokens only (no cookie auth / antiforgery / `IDataProtector`), so Data Protection is genuinely unused → `Builder.cs` filters the category below Error (suppress-at-source).

## BUG-4 — `ConcurrencyException` surfaces as an unhandled 500 on note writes

✅ PR #107 (with BUG-5), 2026-06-02. Optimistic-concurrency conflicts on note writes had no handler/global mapping → 500. Fix: the global handler in `LoggingConfig` maps `ConcurrencyException` → 409 at one cross-cutting point. (Benign races were later also retried — BUG-17.)

## BUG-5 — Renaming a deleted/non-rebuildable note throws an unhandled 500

✅ PR #107 (with BUG-4), 2026-06-02. A pre-check read the eventually-consistent projection, then the domain guard threw a raw `InvalidOperationException` (uncaught) → 500. Fix: `NoteCommandHandler` rebuilds from the stream and throws typed `NoteNotFoundException` via a new `Note.Exists` predicate; the global handler maps that → 404, uniform across all note writes.

## BUG-6 — CloudWatch RUM receives no data (loader CDN host is regional)

✅ `hotfix/12-f-rum-cdn-host`. The RUM loader URL used `client.rum.eu-west-2.amazonaws.com` (NXDOMAIN) — the aws-rum-web loader CDN is global, served only from `us-east-1`; only the data-plane `endpoint` is regional. Fix: hard-code `us-east-1` for the loader host in both deploy jobs; keep `endpoint` regional. Not caught by any gate — a literal string that only fails at runtime DNS in a real browser.

## BUG-9 — Note tab panels stack below Quick notes instead of replacing it

## BUG-10 — Live transcription falls progressively behind realtime

✅ PR #158, deploy #445, 2026-06-03. The AudioWorklet posted ~8 ms (128-sample) chunks → ~125 SigV4-signed event-stream events/sec, more main-thread overhead than sustainable → an audio backlog that never drained. ## BUG-11 — User is signed out too frequently

✅ PR #175, deploy #469, 2026-06-05. Sessions lasted ~1 h because the only refresh was a hidden-iframe `prompt=none` flow modern browsers block (third-party cookies); no refresh token was ever requested. Fix: a backend refresh-token flow — `access_type=offline`, refresh token in an `HttpOnly; SameSite=Strict; Path=/api/auth` `rt` cookie, `POST /auth/refresh` exchanges it; iframe deleted. The 30-day window slides on each refresh.

## BUG-14 — Pasting space-separated tags intermittently drops a pill

✅ PR #205, deploy #495, 2026-06-09. On a freshly-created note `patchTags` no-ops when the note isn't cached, the in-flight GET resolves tagless, and `onSettled` invalidated only `keys.tags` → the first of two concurrent tag adds was lost. ## BUG-15 — Forced through full Google sign-in on cold load (refresh cookie unused at bootstrap)

✅ PR #209, deploy #500, 2026-06-10. Every refresh trigger was guarded on an already-present token, so a cold load (expired token discarded) never tried the `rt` cookie → session effectively ~1 h not 30 days. ## BUG-16 — Google emails the user on every login (`prompt=consent` forces a consent grant)

✅ PR #215, deploy #504, 2026-06-10. `prompt=consent` was hard-coded on every auth URL (added in BUG-11 to guarantee a refresh token) → a fresh consent grant + security email each sign-in. ## BUG-17 — Concurrent multi-word tag add silently drops a tag (no handler retry on conflict)

✅ PR #217, deploy #506, 2026-06-10. BUG-4 mapped a conflict to 409 but never retried, so a benign same-stream race still lost the second tag (its phantom pill then 404'd on removal). ## BUG-22 — Multi-tag add drops a pill under RYW-2 async reads — consistency-token slot overwritten by an older version

✅ PR #262, deploy #551, 2026-06-13. Under RYW-2 async reads, two concurrent same-stream tag POSTs returned `@N`/`@N+1`; the per-stream token slot was last-writer-wins, so the older `@N` could win and the next gated read released before the second tag folded (the server never flags `stale`, so the retry loop couldn't rescue it). Resolved the reopened [TI-19](../technical-improvements-archive.md#ti-19) `TagsJourney` flake (20/20 first try). Follow-up: tag-pill asserts made reload-tolerant.

## BUG-23 — Projection rebuild returns an unhandled 500 on a transient DynamoDB timeout

✅ PR #269, deploy #558, 2026-06-13. ## BUG-27 — Concurrent multi-tag add silently drops a tag (exhausted-retry 409 treated as a duplicate no-op)

✅ Done (under TI-39). On retry exhaustion `NoteCommandHandler` rethrew `ConcurrencyException` → 409, which the client treats as a duplicate-tag no-op → the loser's write was silently dropped under a phantom optimistic pill. Aggravated by 27-D (separate Command-Lambda invocations). Fix: throw `WriteContentionException` on exhaustion → a retriable **503** (distinct from the duplicate 409); `MaxAppendAttempts` 4→6; client retries 503, throwing on the final attempt so a never-landing write rolls back. Lesson: a retriable failure must never share a status code the client treats as success.

## BUG-28 — Concurrent multi-tag add-then-remove drops a write (DynamoDB `TransactionConflict` escaped as an unhandled 500)

✅ Done. The loser of two concurrent `TransactWriteItems` on one stream's META row is cancelled with reason `TransactionConflict`, but `DynamoDbEventStore.AppendAsync` only translated `ConditionalCheckFailed` → `ConcurrencyException`, so the conflict escaped as an unhandled 500 and (not being `ConcurrencyException`) was never retried → silent drop. Not reproducible in-process (the in-memory store has no transaction-conflict semantics). Fix: classify `TransactionConflict` as a retriable `ConcurrencyException` too (extracted + unit-tested); protects every aggregate's concurrent writes.

## BUG-29 — Projector can't purge note images on delete (role missing `s3:ListBucket`)

✅ Done, 2026-06-13. The Projector role had `GrantDelete` (DeleteObject only) but `PurgeNoteAsync` **lists** objects first → every `NoteDeleted` purge threw `AccessDenied (s3:ListBucket)` (caught at Warning), orphaning images in S3 indefinitely. A 27-RYW/27-D IAM gap. Fix: add `imagesBucket.GrantRead(projectorFunction, "notes/*")` (ListBucket+GetObject) alongside GrantDelete; CDK assertion requires a List action (still no PutObject).

## BUG-30 — Note-scoped handlers authorized against the async NoteDetail projection → 404 after create under load

✅ Done. Every note-scoped handler checked ownership via the async `NoteDetail` projection then 404'd on null, so an op right after `POST /notes` hit a not-yet-built projection → a 404 storm under the E2E write burst (invisible in single-user prod; invisible to investigation because the E2E env is a separate AWS account). ## BUG-31 — A browser test ("remove an image, reopen the note") randomly fails during deploys

✅ PR #397, deploy #701, 2026-07-23. `NoteImageJourney.Remove_an_image` randomly red-gated deploys, blocking unrelated releases. **Three stacked causes:** (1) the removed image genuinely reappeared after reopening — fixed by the wider read-after-write work (TI-39 projector warm-up + [BUG-30] event-stream ownership); (2) `SaveAndReturnAsync` waited for a `GET /notes/cards` request the page can serve from its in-memory cache, so the wait timed out at 30 s — fixed (PR #297) by waiting for the home screen instead, which de-flaked the whole suite, not just this test; (3) the #697 failure was **not** a slow reopen — a stale gated refetch transiently **blanked** the note ([BUG-48]), which flips the header Save→Cancel by design (`hasContent` false), so `save-button` was genuinely absent. Also raised the `ConsistencyGate` cap **2 s → 8 s** (PR #377, deploy #681) after prod showed 11 gate timeouts in 14 days, the worst shape a cold overnight projector (`lastSeq=-1`, no recorded position within budget). The first re-enable attempt (PR #393, reload-tolerance on the *reopen*) addressed the wrong cause and was reverted (PR #395). Confirmed **6/6 clean** gate passes (#701–#706). ## BUG-33 — Forced through full Google consent after inactivity (warm-tab refresh skips the `rt` cookie)

✅ Done 2026-06-22, slices **30-C** + **30-B**. Returning to a backgrounded tab showed the full Google sign-in **and scope-approval screen** (~twice a day) despite a valid 30-day `rt` cookie — same user-facing symptom as the supposedly-fixed [BUG-15]/[BUG-16]. Two warm-tab paths treated an expired in-memory token as a dead session **without first attempting a silent refresh**, and both cleared `google_refresh_established` (which forces `prompt=consent` on the next sign-in): `AuthContext.onVisibilityChange`'s `if (remaining <= 0) handleRefreshFailure()` branch (only `remaining < REFRESH_LEAD_MS && > 0` tried the cookie), and `useGoogleAuth.scheduleRefresh`'s `if (delay <= 0) { onRefreshFailure() }`. Chrome freezes background-tab timers, so the proactive 5-min-lead refresh never fired while hidden and `remaining <= 0` was the common case on refocus. Prod confirmed the diagnosis: every Google `/token` call returned **200** on a clean ~55-min cadence and the sign-outs produced **no** failed Google call — the failure short-circuited client-side and never reached `/auth/refresh`. Fix: 30-C collapses both paths into an `attemptSilentRefresh()` first, failing (and clearing the flag) only on a null result; 30-B removed the flag-driven `prompt=consent` forcing entirely, so even a genuine sign-out no longer re-triggers consent. The warm-tab sibling [BUG-15] missed — that fix added only the **cold-load** bootstrap refresh. (Confirmed during diagnosis: the OAuth app is **Published**, so token expiry was never a factor.)

## BUG-34 — In-progress transcript lost on browser-back; re-record couldn't recover it

✅ Done, 2026-06-22 (PR #306, deploy #606). Alt+← (popstate) while recording silently unmounted the note: `beforeunload` doesn't fire on SPA nav and the leave-confirm was wired only to the in-app Save button, so the fire-and-forget unmount commit was aborted on a true page exit → first recording never committed. Re-record couldn't recover it: "Continue" keyed only off the *committed* transcript (`hasInitialTranscript = transcriptText !== null`), so a fresh recording started empty and its commit deleted the note-keyed draft. Confirmed in prod (note `0a449915…`): only the *second* recording's `TranscriptionCompleted` (v41) existed; draft table empty. Fix: (a) popstate guard in `NoteView` (trap history entry → leave-confirm; "Leave & save" exits via `onExit` to a fresh route, not `navigate(-1)` which the trap absorbs) + a `pagehide` keepalive flush in `useTranscription` writing the finalised tail to the loss-tolerant **draft** (never a premature commit); (b) draft-aware Continue — `NoteView` feeds an interrupted draft into `RecordControl` so Record offers Continue seeded from it. Frontend-only; the popstate guard's full browser-history nav is unprovable in jsdom (`BrowserRouter`, no `useBlocker`), so data-safety rests on the unit-tested pagehide flush + unmount commit. See [learning](../learnings/phase-bug34-transcript-leave-guard.md).

## BUG-35 — Fuzzy search over-matches ("Andrew" returns notes containing "and")

✅ Done, 2026-06-22 (PR #312, deploy #612). `NoteSearchRanker.Score` ranked a query against each **whole field** with `Math.Max(Fuzz.PartialRatio, Fuzz.TokenSetRatio)`. `PartialRatio` slides a query-length window across the entire body and keeps the best substring match — over a long note there are hundreds of windows, so a 6-char query almost always found an "and…" window scoring ≥ the 60 threshold. Matching was substring-based, not word-based. Fix: word-level matching — a query term matches a document **token** only by (1) exact equality, (2) prefix (term ≥ 3 chars; `Andrew`→`Andrews`), or (3) tight whole-token `Fuzz.Ratio ≥ 85` (term ≥ 4 chars; `planing`→`planning` ≈ 93, `and`→`andrew` ≈ 67 rejected). Inclusion gates on the strongest single-term hit (OR semantics across a multi-word query); ranking uses the mean per-term score (rewards full coverage) with the existing 1.5 title weight. 4 regression tests (name-vs-"and", prefix, infix, multi-word OR) + preserved typo test; query-time change in the ranker so no projection backfill needed. See [minor-log](../learnings/_minor-log.md) 2026-06-22 BUG-35.

## BUG-37 — The ✓ "Mark as discussed" tick on a note heading no longer works

✅ Done, 2026-06-25 (PR #344, deploy #645). The floating ✓ tick fires `editor.commands.toggleStrike()` while the selection is only a **collapsed caret** inside the heading (the button renders on `isActive('heading')`, no text selected). ProseMirror `toggleMark`/`toggleStrike` on an empty selection only sets a **stored mark** (it would strike the *next typed* char) — it never strikes the existing heading text, so nothing visibly happened. The click handler was unchanged since 7-B; 7-B's "renders with strikethrough" acceptance was hand-checked, never covered by an automated test, so the regression (surfacing across the TipTap v2→v3 line) went unnoticed. Reproduced empirically first: caret-only `toggleStrike` yields no `~~` in the serialized markdown; range-selecting the heading text first does. Fix: extracted `web/src/lib/headingDiscussed.ts` — `markHeadingDiscussed(editor)` range-selects the heading (`$from.start()`→`$from.end()`) then `toggleStrike`, guarded on `isActive('heading')`; the ✓ button calls it. New unit spec `headingDiscussed.test.ts` drives a real headless `Editor` with the same collapsed caret the button produces (strike-on, toggle-off, heading-only, empty-heading no-op), RED-first then GREEN. Frontend-only, no event/projection change. See [minor-log](../learnings/_minor-log.md) 2026-06-25 BUG-37.

**Follow-up (PR #347, deploy #648) — the actual primary cause.** #344's fix was real but *secondary*: the tick still did nothing in the real browser. Root cause: the ✓ button is `position:absolute` with **no z-index**, and the editor content `.contentInput` is `position:relative` (added in Phase 25 for inline-image positioning) — so the content is a positioned sibling in the *same* stacking layer and, coming later in the DOM, paints **over** the button, swallowing every click (the click landed on the heading, not the button). Invisible to jsdom (no layout/hit-testing), which is why #344's unit tests were green while the feature stayed dead. Proven in a real browser (Playwright): `elementFromPoint` at the tick centre returned `<h2>` before the fix and the `BUTTON` after; a normal click then strikes the topic. Fix: `z-index:1` on `.discussedButton`. Added `DiscussedTickJourney` (Browser.E2E) — a normal `ClickAsync` on the old code times out with "`<h2>` … intercepts pointer events"; passes on the fix. Both fixes are needed: #347 makes the click land, #344 makes a caret-click strike the whole heading. See [minor-log](../learnings/_minor-log.md) 2026-06-25 BUG-37b.

## BUG-38 — Typing a tag on a freshly-opened note could have the box ripped away mid-word

✅ PR #418, deploy #722, 2026-08-07. **The worst deploy-gate flake in the project's history, and a real user bug — not a test artefact.** Start typing a tag on a note that is still loading and the input can vanish with the half-typed text silently submitted. Cause (`NoteView.tsx:267-269`): `useEffect(() => { if (!loadingDetail && !notFound) inputRef.current?.focus() }, [loadingDetail, notFound])` focuses the **title** input — not on mount, but whenever the RYW-gated `GET /notes/{id}` resolves, i.e. at an arbitrary moment from ~150 ms to the 8 s gate cap, while the screen has been interactive the whole time. The tag combobox dismisses on blur (`TagCombobox.tsx:107` → `CommandBar.tsx:81`), so the focus grab **unmounts** the input. Fix: autofocus made mount-only and only when nothing else holds focus; `AddTagAsync`'s catch widened to `PressAsync` + `TimeoutException`; regression test red against the old effect.

**Measured scale:** a per-attempt scan of deploys #627–#719 (93 deploys) found 58 failing-test occurrences, **26 of them `TagsJourney`** (45%, ~4× the next worst journey), across 15 deploys and hitting all six of its tests. The doc had recorded **6** — the 4× undercount is failures re-run into green and never written down, and is why the standing rule is to count per-attempt with `scripts/flake-watch.sh`, never by reading run conclusions. Same mechanism explained `ActionEditJourney` (5 occurrences); `ActionsSection` has the identical blur-to-unmount shape.

**Retired theories** (all disproved): cold start / idle gap (#719 failed 43 s in, warm, after 27 passes); projector lag (lag cannot detach a DOM node, and the failing call is an *action*); the app never loaded (the input **resolved**, `value="1:1s"`); a `notFound` bounce. Lag was the trigger's timing source, never the fault — which is why every consistency-token fix looked relevant and none worked. **Method note:** the breakthrough came from deploy #719's `locator resolved to …` line, the first ever captured, because the enriched diagnostic (#372) wrapped only `FillAsync` and not `PressAsync` — a gap this row flagged for months that cost the root cause every time. Bar met at 10/10 clean deploys (#722–#731), per-attempt.

## BUG-39 — Todo reorder reverts after reload (deployed only)

✅ Done 2026-06-26. Dragging BBB above AAA then reloading reverted the order — deployed-only and deterministic (5/5 across deploy #656 and its reruns). **Root cause, from the test-env Projector Lambda log (`Projector skip todo-order#__default__ at 1: position_guard`): `clear-test-data` wiped `notetaker-events` and the projection tables but **not** `notetaker-proj-position`**, the projector's per-stream processed-sequence store. The default workspace's order stream `todo-order#__default__` has a **stable id reused every run**, so once any run set its position to seq 1 that mark survived the clear; every later run re-appends its reorder as seq 1 (events re-numbered from 0), which is `≤` the stale mark → the position guard skips it as an already-seen duplicate → positions are never applied → `GET /todos` falls back to `AddedAt` order. Entity streams (`note#`, `todo#<guid>`) dodge it because each run uses fresh guids; only **stable-id** streams collide. Not a product bug and **not 36-B** — that correlation was coincidental (#655 was the run that first set the mark, and it passed). Fix: `clear-test-data` also clears `notetaker-proj-position` plus the previously-omitted projection tables (`notesearchview`, `workspacelist`, `actionfeedback`, `tagfeedback`, `calendarlinkindex`); `TodoReorderJourney` un-quarantined. ## BUG-40 — Blank lines a user adds for structure are stripped on save

✅ PR #363, deploy #666 (`70c87c4`), 2026-06-26. Frontend-only. A note typed with blank lines between sections was condensed into a single tight block on save. ## BUG-47 — Stale-read note edit silently overwrites real content (no version guard) → data loss

✅ PR #392, deploy #696. **High — real data loss:** a full note was wiped in prod (recovered from the event stream and restored). A user edited a note, navigated away and returned; the note showed **empty**; they retyped what they remembered, and the save replaced the original with the fragment — no warning, no conflict. Prod evidence (stream `note#c7b3b612…`): `v5 ContentEdited` 2134 chars @09:04:06, `v6` 30 chars @09:04:14, the fragment verbatim the last bullet of v5. v5 was durably stored the whole time; only the read model reflected v6. **Three combining gaps:** (1) the note-detail read is served by the async projection behind a best-effort gate that caps at 8 s and then returns the current projection with a `stale` header, while the client `gatedRead` retries only 2×/300 ms and **returns the stale body anyway** (a missing token reads ungated); (2) the Tiptap editor is **uncontrolled** — content is taken once at `useEditor` construction with no later value-sync, and `LazyNoteEditor` is keyed by `noteId`, so navigate-back **remounts** and reseeds from `contentDraft ?? detail?.content ?? ""`, making a stale-empty read the editable baseline; (3) `EditContentCmd` had no check that the client had seen the latest content — the event store's append-level optimistic concurrency guards the *store* version, not the version the *client* was looking at, so the overwrite appended cleanly. Fix: **hash-based optimistic concurrency on content edits** — the client sends the SHA-256 of the content it loaded, the aggregate compares it to a hash of its current `_content`, and a mismatch returns a **terminal 409** (not 503 — a retry can't help, per [BUG-27]), surfaced as a non-destructive conflict banner that keeps the typed text and offers "Load latest content". Hash chosen over a content-version field (which would need a `NoteDetail` field mapped in **both** stores plus a round-trip test and a projector change) and over the whole-stream token (which false-conflicts on an interleaved tag/date write); `ContentEdited`'s shape is unchanged, so no event versioning and no prod backfill. Explicitly rejected: a size/shrink heuristic (can't distinguish a deliberate select-all-delete from a stale wipe) and server autosave (would persist stale-empty state *faster*). The read-side analogue — a stale refetch regressing the cached detail — remained open as [BUG-48]. See [learning](../learnings/phase-bug47-stale-read-content-overwrite.md).

## BUG-48 — A note could flash blank when reopened

✅ PR #436, deploy #740, 2026-08-08. The durable fix is moving analysis off the synchronous request path ([TI-63]); anything needing >23 s + tail cannot fit a 29 s Lambda at all.

## BUG-65 — On-device live transcription worked, but was far slower than the ~3-4 s target

✅ PR #435, deploy #737, installer `1.0.0-20260808.182`. **CLOSED 2026-08-10 on measured hardware.** After [BUG-56] the server ran and live text appeared, but well behind [BUG-53]'s target. Four compounding causes, diagnosed from the code and the pinned v1.9.1 server source: (1) the live server was spawned with **no streaming flags** — `--audio-ctx` unset, so every `/inference` paid the **full 30 s padded encoder cost** regardless of window length; (2) `--no-fallback` unset, so temperature fallback silently retried a messy segment up to ~6× (0.0 → 1.0 in 0.2 steps), and a sliding window's clipped boundary words are exactly what trips those heuristics; (3) `maxWindowMs = 8000` meant the reducer committed nothing until the window exceeded 8 s, so the steady-state re-transcribed window was **8-16 s**, not the ~3 s the header comment assumed; (4) threads at `floor(cores/2)` from [BUG-52]'s CPU-peg fix. Beam search was **ruled out** by reading the source (`beam_size = -1` → already greedy).

**The asymmetry that made it cheap:** the live transcript is *disposable* — 48-B re-transcribes the whole recording with small.en at stop and replaces it — so live accuracy can be traded hard for latency with no effect on the saved transcript. Fix: `--audio-ctx 768` on the live server only, `maxWindowMs`/`hardWindowMs` halved to 4 s/8 s, a **send-time clamp** so the window handed to the engine can never exceed the encoder context (overshooting made whisper truncate the mel while still seeking a full 30 s, skipping audio outright — the old `hardWindowMs` "invariant" bounded nothing, since `finalizedMs` only advances after an inference completes), and a `<userData>/local-transcription.log` recording per-step `window`/`infer`/`rtf`/`dropped`/`clamped`. Threads deliberately **not** raised — reduce work before spending CPU. `--no-fallback` was deliberately not passed: it is parsed by the server and **never read** (dead in every release through v1.9.1), and the only working lever also disables whisper's repetition guard, which a reduced `audio_ctx` is documented to *induce*.

**Measured, not asserted:** an installed build had no observable channel at all, which is why BUG-56 and BUG-65 both had to be diagnosed by reading code — hence the log, scored by `scripts/check-local-transcription-log.sh`. Three sessions ran `rtf` median 0.30 → 0.26 → **0.13** (about 8× faster than realtime) as the machine warmed; on the final 48-step recording, max 1.39 on the very first step only (model warm-up), 1 of 48 steps ≥1.0, 1 dropped tick, 0 clamped, 0 failed. Two Hawk rounds each found the fix reproducing the bug's own shape — a no-op flag asserted as working, and a runaway guard the new clamp could pin below its threshold; see [phase-bug65-guards-that-cannot-fire](../learnings/phase-bug65-guards-that-cannot-fire.md).
